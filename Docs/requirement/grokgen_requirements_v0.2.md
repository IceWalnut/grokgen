# grokgen v0.2 需求：Civitai 浏览、下载与「照着做一遍」

**状态**：草稿 · 2026-09-23
**上游**：`Docs/requirement/grokgen_requirements_v0.1.md`（v0.1 的范围与约束仍然全部有效）
**这份文档只记 v0.2 新增的东西。** v0.2 开工之前，v0.1 的 M1〜M6 要先走完。

⚠️ **这是一份记录想法的草稿，不是可以直接开工的需求。**
里面有三处**已经实测确认的阻塞问题**（§3），它们决定了这个功能能做成什么样。
在那些问题有答案之前，不要往下游推契约和架构。

---

## 1. 想做什么

用户平时逛 Civitai。现在的流程是：在网页上看中一个模型 → 手工下载 →
想办法弄到服务器上 → 再去 ComfyUI 里用。看中一张图想复现它的效果，
就手工把 prompt 抄下来。

**v0.2 想把这一整段搬进 App：**

| 想要的 | 一句话 |
|---|---|
| **逛** | 在 App 里浏览 Civitai 的模型和图片（SD 的、MiniMax H3 的都算） |
| **拉** | 看中一个 LoRA 或 checkpoint，**点一下就让服务器开始下载** |
| **抄** | 看中一张图，**把它那一整套 prompt 和参数搬过来**，在自己的服务器上跑一遍 |

⭐ **注意「点一下就让服务器开始下载」这件事的形状**：下载发生在**服务器**上，
不经过手机。手机只是遥控器 —— 这和整个项目的定位是一致的（App 是薄前端）。

---

## 2. 一个先要纠正的假设：不用写爬虫

用户原话里提到「用 python 爬虫，还是什么途径」。**实测确认：Civitai 有官方
REST API，从开发机直接可达。**

2026-09-23 实测（`curl https://civitai.com/api/v1/models?limit=1&types=LORA`）：

```
HTTP 200
顶层键: ['items', 'metadata']
```

单个模型版本里能直接拿到的字段，**每一个都正好对应一个我们需要的东西**：

| 字段 | 实测值举例 | 我们拿它干什么 |
|---|---|---|
| `baseModel` | `"SDXL 1.0"` | ⭐ **解决 v0.1 §8.6 那个难题**，见 §5 |
| `downloadUrl` | `https://civitai.com/api/download/models/135867` | 服务器照着下 |
| `files[].sizeKB` | `223097` | **下载前就能算出要占多少盘**，见 §3.1 |
| `files[].hashes.SHA256` | 有 | 校验下载完整性；也能用来判断「这个我是不是已经有了」 |
| `trainedWords` | 有 | LoRA 的触发词。**没有它，下载下来的 LoRA 多半用不对** |
| `virusScanResult` / `pickleScanResult` | 有 | Civitai 自己扫过，把结论如实显示给用户 |

⇒ **浏览和下载这两件事不需要爬虫。** 用官方 API，稳定、有结构、不会因为
网页改版就坏掉。

⚠️ 但下面第三件事（抄 prompt）**恰恰是 API 不给的**，见 §3.3。

---

## 3. 三个已经实测确认的阻塞问题

**这一节是这份文档最重要的部分。** 三个问题都不是「实现难度」，
是「前提还不成立」—— 在它们有答案之前，这个功能的形状定不下来。

### 3.1 磁盘会被填满，而且很快

2026-09-23 实测服务器：

```
/dev/sdd  251G 总量  138G 已用  101G 可用  (58%)
模型已占：ComfyUI 37G + SD WebUI 36G = 73G
```

**只剩 101 GB。** 而 Civitai 上一个 SDXL checkpoint 通常 6〜7 GB ——
**点十几下就满了**，而且「点一下就下载」这个交互本身就是鼓励多点的。

⇒ 硬要求：

- **下载前显示这个文件多大、下完还剩多少**，不是下完才发现
- **空间不够时拒绝，并说清还差多少**，不要下到一半失败
- 需要一个**管理已下载模型的地方**：列出来、看占用、删掉不要的
- ⚠️ **删除要谨慎**：ComfyUI 的模型目录里混着用户自己早就放好的模型
  （见 v0.1 §8.6，那 39 个 LoRA 里大部分不是我们下的）。
  **App 只能删自己下载的那些**，这要求网关记账 —— 哪些是它下的。

### 3.2 下载是长任务，但它**不能**走现有那个队列

现有的任务队列容量是 1，**那是为显存设计的**（v0.1 §F7：同一时间只允许一个
重 GPU 任务）。而下载**一点显存都不占**，它占的是网络和磁盘。

⇒ **两者必须分开。** 把下载塞进那个队列会造成一件很蠢的事：
下载一个 7 GB 的模型期间，整台机器不能生成任何东西。

所以需要**第二条队列**：可以并发、可以和生成同时进行、失败可重试、可断点续传。
它和生成任务共用「任务」这个概念（状态、进度、取消），但**不共用那个容量为 1 的闸门**。

⚠️ 这件事会影响 v0.1 已经写好的任务状态机 —— 到时候是加一个「任务类型」
维度，还是另起一套，要在 v0.2 开工时定。**现在不改代码。**

### 3.3 ⚠️ 「抄 prompt」这条，公开 API 拿不到数据

**这是三个问题里最严重的一个，因为它直接决定这条需求能不能做。**

实测（2026-09-23）：

| 测了什么 | 结果 |
|---|---|
| `GET /api/v1/images?limit=100` | 100 张图，**有生成参数的 0 张** |
| 模型详情里附带的 15 张示例图 | **`hasMeta: true` 15/15、`hasPositivePrompt: true` 15/15，但 `meta` 字段是空的** |

⇒ **Civitai 明确知道哪些图有生成参数（它返回了标志位），但公开 API 不返回参数本身。**

这不是「我们没找对字段」，`hasMeta` 这个标志的存在本身就说明数据在那儿、
只是没给。可能的原因和对应的路子：

1. **要 API key** —— Civitai 支持 API key。最可能，也最该先试。
   ⚠️ **还没试过**，因为得先去申请一个。
2. **参数只在网页上** —— 那就得解析网页，回到「爬虫」那条路，
   而且会因为网页改版就坏。
3. **Civitai 主动收紧了** —— 如果是这样，这条需求要么放弃，
   要么退化成「把图下下来，让用户自己看图上的水印/描述」。

⇒ **v0.2 开工前必须先回答这个。** 办法很便宜：申请一个 Civitai API key，
带上它重跑一次上面那两条 curl，看 `meta` 是不是就有了。
**在这之前，「抄 prompt」这条需求的可行性是未知的，不要按它已经成立来设计 UI。**

## 4. 「照着做一遍」比看起来难：抄来的参数不能直接用

就算 §3.3 解决了、参数拿到了，**也不能直接塞进我们的 workflow**。
用户原话里已经点到了这个（「需要提示，比如 4080 不够用，或者当前 server 上缺少模型」），
展开是四类检查：

### 4.1 底模在不在

Civitai 的图会写它用的是哪个 checkpoint。**服务器上多半没有那一个。**

⇒ 要明确告诉用户：「这张图用的是 `XXX`，你的服务器上没有。
**要不要一起下载（6.5 GB，下完还剩 XX GB）？**」
—— 把「抄 prompt」和「下模型」这两件事**在同一个界面里串起来**，
而不是让用户自己发现缺东西。

### 4.2 LoRA 在不在，以及触发词

同上，而且 LoRA 还多一层：**没有触发词，LoRA 基本不起作用**。
好在 `trainedWords` 字段 API 是给的（§2）。

### 4.3 显存够不够

用户特别提到了这条。SDXL 出图在 16 GB 上没问题，但：

- 一次出多张、高分辨率、开超分（v0.1 §8.2 提到那两个超分开关很吃显存）
- 抄来的参数可能是别人在 24 GB 卡上跑的

⇒ **在提交之前估一下，不够就提示并给出改小的建议**（降分辨率、减张数、关超分）。
⚠️ 这个估算怎么做还不知道 —— 现在网关只会读实时显存，不会预测。

### 4.4 采样器和参数对不对得上

Civitai 的图大多来自 A1111 或别人的 ComfyUI 工作流，采样器名字、调度器、
CFG 的含义**和我们的 workflow 不一定一一对应**。

⇒ 需要一层**映射 + 兜底**：能对上的就对上，对不上的用我们的默认值，
并**明确告诉用户哪几项没能照搬**。

⚠️ **不要静默地把对不上的参数丢掉。** 那会让「照着做一遍」的结果和原图差很远，
而用户找不到原因 —— 这和 v0.1 里反复出现的那类「不会报错的错误」是同一种。

---

## 5. ⭐ 一个顺带的好处：这件事能解决 v0.1 的一个难题

v0.1 §8.6 记着一个没解决的问题：

> ComfyUI 的 `/object_info` 只给一个平铺的文件名列表，
> **不告诉你哪个 LoRA 属于哪个底模**，而两个池子混在同一个目录下。
> 文件名是唯一线索且不可靠。

**而 Civitai 的 API 每个模型版本都带 `baseModel`**（实测：`"SDXL 1.0"`）。

⇒ **凡是通过这个功能下载的模型，底模归属是已知的** —— 下载时顺手记进
网关自己的账本，M6 那个分类问题对这部分模型就不存在了。

⚠️ 但它**解决不了存量**：服务器上现有那 39 个 LoRA 是手工放进去的，
没有来源信息。所以 §8.6 的三条候选做法仍然需要，
**Civitai 这条只是让以后新增的模型不再产生同样的问题。**

⇒ 这也反过来给 M6 一个设计提示：**那个账本要能同时容纳「手工登记的」
和「下载时自动记的」两种来源**，不要设计成只有后者。

## 6. 还没想清楚的

按「必须先答」排：

1. **§3.3 那个 API key 能不能拿到生成参数** —— 决定「抄 prompt」做不做得成。
   最便宜的验证：申请一个 key，带上它重跑那两条 curl。
2. **下载队列和生成队列怎么共存** —— §3.2。影响已有的任务状态机。
3. **网关怎么记账「哪些模型是它下的」** —— §3.1 的删除功能和 §5 的底模归属
   都依赖它。存哪（和媒体库索引同一个地方？）、记什么。
4. **浏览界面到底展示什么** —— Civitai 的模型列表很长，手机屏幕很小。
   是做成完整的浏览器，还是只做「搜索 + 我收藏的」？
   ⚠️ 倾向后者：**在手机上复刻一个 Civitai 网页没有意义**，
   用户要的是「我已经看中了，把它弄到服务器上」这个动作。
   但这条**没定**。
5. **NSFW 内容怎么处理** —— API 有 `nsfwLevel` / `browsingLevel` 字段，
   可以过滤也可以不过滤。这是个产品选择，不是技术问题。
6. **Civitai 的速率限制** —— 实测时撞到过一次
   `"Image search is temporarily overloaded — please retry."`。
   ⇒ 需要重试和缓存，不能每次翻页都打一次上游。
7. **MiniMax H3 的模型在 Civitai 上有多少** —— 用户说「SD 也好，
   minimax-h3 也好」，但 **H3 是个相对小众的生态，Civitai 上的量级没查过**。
   如果几乎没有，那这个功能实际上就是「给 SD 用的」，范围会小很多。
