### 已解决（M1R7 补跑）

✅ ~~冷启动耗时~~ —— 实测：显存清空后重载 **94 秒**（热启动 75 秒，只多付约 19 秒）。
`job_timeout_seconds` 据此定为 **1800 秒**。
⚠️ **但「ComfyUI 进程重启后从磁盘读 29 GB」那一次仍未测**，见下。

✅ ~~7869 的防火墙规则~~ —— 已加，三条规则全部限定来源为 Tailscale 的
IPv4 与 IPv6 地址段，脚本改成了能自愈（以前重跑不会收紧旧规则）。

✅ ~~`running` 状态在真实链路上是否可达~~ —— M1R7 冒烟实测通过，
转移轨迹 `preparing@0s → running@1s → done@75s`。

✅ ~~`interrupt()` 之后 `/history` 里那条记录长什么样~~ —— M1R7 实测，
**而且推翻了代码里的假设**：`status_str="error"` 但 **`completed=False`**。
网关原来用 `completed` 判断「执行结束了没有」，那个字段的真实含义是
「成功完成」—— 于是被中断和报错的任务永远等不到终态。已修（见 M1R6R7 总结 §1）。

### 挡住 M2（Android 原型）

- ⬜ **进度怎么推给 App**：转发 ComfyUI 的 WebSocket，还是让 App 轮询。
  影响 App 端的实时性与耗电。
  ⚠️ M1R5 之后这条多了一个具体后果：**`stage` 与 `progress` 在 M1 恒为空**。
  `GET /queue` 只能回答「是不是在跑」，回答不了「跑到哪一段」。
  而需求 F2 明确要求把分钟级的 `loading_model` 单独显示出来 ——
  App 上把它和采样混成一个「生成中」，用户会以为卡死了。
- 🔄 **接口契约按实际实现回填**：任务那一节（§2）M1R5 已回填 ——
  删掉了 `advanced`（它把两套采样 profile 的旋钮单独暴露出去，
  等于让需求文档 §8.2 犯过的混用错误重新变成可达状态）、换成 `turbo`；
  `normalized` 补齐九个字段；定义了列表接口的响应形状与取消的语义。
  **剩下 §4 媒体库、§5 GPU、§6 事件流仍是草案**，各自等 M3 / M4 / M2。

### 挡住 M3（媒体库）

- ⬜ **⚠️ `job_id` 的序号在网关重启后会重复**：序号是进程内的，
  重启后从 `0001` 重来，同一天重启两次就会产生两个相同的 `job_id`。
  M1 状态不持久化、重启后旧 id 本来也查不到，所以现在影响为零 ——
  但**做持久化时必须先解决它**，否则会撞主键。
- ⬜ **任务与媒体的元数据存哪**：SQLite 还是 JSON 索引文件。
  倾向 SQLite（要分页和按来源过滤）。
- ⬜ **缩略图什么时候生成**：任务结束时顺手做，还是首次访问时懒生成。
  倾向前者，那时文件刚写完、磁盘缓存还热。
- ⬜ **任务状态持久化**：M1 只存内存，网关一重启就丢。

### 挡住 M4（接入 SD）

- ⬜ **SD 的两代模型怎么处理**：`v1-5-pruned-emaonly` 是 SD 1.5，
  其余三个（6.5–6.7 GB）看着像 SDXL 系。**两代 workflow 不一样** ——
  要么只支持一代，要么按模型类型分别拼图。

  可能再次发生**（runbook §6.5）。
- ⬜ **`input/grokgen/` 的上传图没有清理机制**，会一直堆积。M3 媒体库一起处理。
