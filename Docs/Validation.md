# 验证标准

**执行文档里每个 round 的「判据」一栏，引用的就是本文件定义的层级与 VS 编号。**

本文件**两端共用**：`server/`（FastAPI 网关）与 `app/`（Android 客户端）
遵守同一套层级和同一套 VS 编号。理由和接口契约放根目录是同一个 ——
**跨两端的验证场景不该被编两个号**，验证的规矩也不该被抄两遍。
两端不同的只有**命令**，见 §2 的表。

---

## 1. 这个项目为什么需要专门的验证标准

三件事在这个项目里机器判不了，而它们恰好是产品的核心：

1. **视频画面是不是正常的。** 任务成功、格式正确、时长对，画面仍然可能是一片黑或纯噪声。
2. **首帧图有没有真的生效。** 首帧参数传错时，任务会**正常成功**，只是悄悄变成了一个 T2VA。
3. **手机上播得顺不顺。** 能不能拖进度条、起播要等多久。

⇒ **Level 0–3 的自动化不是为了替代眼睛，而是为了保证在两次人眼检查之间不发生静默回退。**

---

## 2. 验证层级

### Level 0：文档检查

- `Docs/TODO.md`、`Docs/ContextPack.md` 已按本轮改动更新
- 受影响的需求 / 契约 / 架构 / 执行文档已同步
- 本轮若推翻了某个决策，**改的是上游文档，不是绕过它**（`AGENTS.md` §2）

### Level 1：构建与分层检查

| 端 | 命令 |
|---|---|
| server | `server/.venv/bin/python -m pytest --collect-only`（导入期错误在这里暴露） |
| app | `./gradlew build` |

⭐ **网关有一条可执行的分层判据**：

> 在**开发机上、不连服务器**的情况下，除 `comfy/http_client.py` 外的全部测试应当通过。
> **跑不通就说明有人把 ComfyUI 调用漏到 `core/`、`media/` 或 `api/` 里了。**

这条是架构文档 §3 那个"唯一硬约束"的检验形式。它是 `VS-13`。

### Level 2：自动化测试（不需要 GPU）

| 端 | 命令 |
|---|---|
| server | `server/.venv/bin/python -m pytest -m "not integration"` |
| app | `./gradlew test` |

这一层跑在**开发机**上，不占 GPU、不连服务器。
**workflow 构造、帧数换算、prompt 拼装、状态机全部属于这一层** ——
它们是纯逻辑，没有理由等到占用 GPU 才发现写错了。

⚠️ **workflow 的 golden 文件不提供自动覆盖开关。**
有了它，"改坏了"和"改好了"就是同一个动作。
期望文件的每一处变化都要人工看过 diff 再手动更新。

### Level 3：真实链路验证（连 ComfyUI，占 GPU）

```bash
server/.venv/bin/python -m pytest -m integration    # 默认跳过，手动触发
scripts/smoke_m1.sh                                 # 端到端冒烟
```

⚠️ 跑之前先确认 ComfyUI 没在忙：

```bash
curl -s --noproxy '*' http://icewalnut-1060.tail22a711.ts.net:8188/queue
```

⚠️ 从开发机发请求**必须带 `--noproxy '*'`**，否则本机代理会拦截并返回 502
（runbook §6.4）。

### Level 4：人眼判定（必须做，但不是构建闸门）

- 视频画面正常，不是黑屏或噪声
- I2VA 的首帧**可辨认是上传的那张图**
- 手机上能拖进度条，起播没有明显等待

⚠️ **这一层只报告"这次看过了"，不参与自动化。**
但**不做不等于通过** —— round 总结里必须写清这一层看了什么、没看什么。

## 3. 验证场景（Validation Scenario, VS）

VS 编号**跨里程碑稳定**：一旦分配就不改用途。废弃时保留编号并标注原因。
新增时追加编号，**不复用旧号**。

### 三条关于覆盖面的记账规则

**① 「语料里没有」和「构造不出来」要分开记。**
某个分支在真实使用中从不触发，但输入构造得出来 ⇒ **补构造用例**。
某个分支任何输入都构造不出来 ⇒ **不要补端到端用例**，那只会得到一个绿色但与产品行为无关的测试；
在代码注释里写明它何时会变成可达。

**② 只证明"坏的消失了"不够，要有一个正向的数。**
例如验证对齐指令行时，"没有报错"和"输出里没有多余空标签"都是负向的；
**还要断言那一行确实出现了，且秒数是 `5.17` 而不是 `5.00`。**
把整段删掉也能让负向断言通过。

**③ 一条从未被触发过的回落分支，不算验证过。**

## 4. 两条不许违反的规矩

### 4.1 测完了不许改判据

实测没达到判据时，只有两种正当处置：

- **前提被推翻** ⇒ 回去改上游文档，并说清是哪条前提错了；
- **实现有难度** ⇒ 改代码。

**"把阈值放宽到刚好通过"两种都不是。** 判据是在测之前定的，
测完再改它，这条判据就永远不会失败 —— 而**一条从未失败过的判据不是判据**。

未通过就如实记成未通过，**跟着那个里程碑的退出评审走，不得在同步文档时消失**。

### 4.2 性能数字必须带测量条件

任何耗时、显存、吞吐的读数，记录时要一并写下：
**在哪台机器、什么负载状态、用的什么输入、跑了几次取的什么值**。

不带条件的性能数字**不可复现**，而"结论必须可复现"是 `AGENTS.md` §5 的第一条。
两次读数差很多时，没有这些条件就无法排查差异从哪来。

⚠️ 这一条在这个项目里格外容易出问题：**GPU 任务的耗时受显存是否已加载模型影响极大**
（模型加载是分钟级的固定开销，runbook §6.6）。
一个"生成用了 2 分钟"的读数，**不写清模型是否已经在显存里，等于没写**。

## 5. 每轮必交的验证报告

每个 round 结束时，在 `Docs/experience/YYYY-MM-DD/M<n>R<m>_*.md` 里记录：

- **验证了什么** —— 层级 + VS 编号 + 实际命令 + 实际输出
- **没验证什么** —— 以及为什么
- **哪些验证失败了**
- **下一轮遗留哪些风险**

⚠️ **「没验证什么」不是可选项。** 只写通过的部分，
会让下一轮的人误以为覆盖是完整的 —— 那比不写更糟。
