# 文档放哪

这个仓库有**两端**（`app/` 与 `server/`），文档按「给谁看」分三层。

```text
grokgen/
├── Docs/                  ← 产品级 + 两端共享
│   ├── requirement/       产品需求：做什么、不做什么、验收标准（覆盖两端）
│   │                       v0.1 是当前在做的；v0.2 是记录中的想法，还不能开工
│   ├── contract/          App 与网关之间的接口契约  ★ 两端都读
│   ├── runbooks/          怎么连服务器、怎么起停服务（两端都要）
│   ├── knowledge/         外部来源的原始材料，只读不改
│   ├── experience/        每个 round 的会话总结，按日期分目录
│   ├── Validation.md      验证层级与 VS 编号  ★ 两端都读
│   ├── TODO.md            任务与里程碑跟踪
│   └── ContextPack.md     会话引导上下文
│
├── server/Docs/           ← 只有网关关心
│   ├── architecture/      网关怎么分层、怎么拼 workflow
│   └── implementation/    每个里程碑的执行文档
│
└── app/Docs/              ← 只有 Android 客户端关心（开发 App 时再建）
    ├── architecture/
    └── implementation/
```

## 判断一份新文档该放哪

问一句：**另一端需要读它吗？**

- **两端都读 → 根 `Docs/`。** 需求、接口契约、验证标准、服务器 runbook 都属于这一类。
- **只有一端读 → 那一端的 `Docs/`。** 网关的分层设计、App 的页面结构。

⚠️ **验证标准也放根目录，理由相同。** 层级和记账规则不分语言，
而且**跨两端的验证场景不该被编两个号** —— 两端不同的只有命令，那是一张小表。

⚠️ **接口契约必须放根目录，这一条没有例外。**
它放进 `server/Docs/` 的话，App 那边会抄一份；两份慢慢对不上，
而且**没有任何机制会报错** —— 契约不是代码，编译器不管它。

## 为什么需求文档不跟着拆

`Docs/requirement/` 里那份是**产品需求**：它描述的是「手机上能做什么」，
F1–F7 全是 App 的功能，但每一条都要网关配合实现。
拆成「App 需求」和「网关需求」会让同一件事被写两遍。

**如果将来某一端有自己独有的、另一端完全不关心的需求**，再在那一端建
`Docs/requirement/`。到那时根目录这份仍然是产品级的总纲。

## 里程碑与轮次的命名

- **M = Milestone**，产品级，跨两端。M1…M5 的划分见
  `Docs/requirement/grokgen_requirements_v0.1.md` §9。
- **R = Round**，一个 round 的定义见 `AGENTS.md` §1.1 ——
  为解决一个明确问题所做的一次完整努力，**不等于一个步骤，也不等于一条聊天消息**。
- 合起来写作 `M1R3`。

一个里程碑如果两端都要动，**两端各写一份执行文档**，
例如 `server/Docs/implementation/M2_*.md` 和 `app/Docs/implementation/M2_*.md`。
不要写成一份由两端共同编辑的文档 —— 那样每次改动都要同时理解两端。

## 移动文档时

引用都是散文里的路径，**失效了不会报错，只会误导下一个读者**。
移动时在同一次改动里把所有引用改掉，然后 `grep` 一遍旧路径确认没有残留。
