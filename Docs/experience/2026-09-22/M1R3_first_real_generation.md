**结论**：都通过。VS-5 / VS-6 / VS-7 全过，并新增 VS-14（提交前预检）。

## 1. 中途被一个环境问题卡住，根因定位清楚了

开工没多久，**ComfyUI 的 8188、WSL 的 SSH 2222、网关的 7869 从外面全部连不上**，
而 Windows 本体的 22 端口正常。

**排除掉的**：不是 runbook §4 那个坑。WSL 发行版**没有**被回收 ——
它连续运行了 1 天 3 小时，`sshd` 正常监听 `0.0.0.0:2222`，
Tailscale 地址也确实镜像进了 WSL（`eth1: 100.64.3.34`）。

**决定性证据**（在 Windows 本机上测，不经过 Tailscale 网络）：

| 目标 | 结果 |
|---|---|
| `127.0.0.1:2222` | ✅ 通 |
| `127.0.0.1:8188` | ✅ 通 |
| `100.64.3.34:2222`（本机自己的 Tailscale 地址） | ❌ 不通 |

最后一条纯粹是本机内部投递，所以问题不在网络路径上。

**根因**：WSL 镜像网络那层的 Hyper-V 防火墙 `DefaultInboundAction = Block`，
而入站规则里只有一条 `MPSSVC Loopback Allow Rule` —— **只放行环回，
没有放行外部入站**。这与观察完全吻合。

**处置**（用户批准后执行）：加两条针对性的 Hyper-V 入站放行规则。
按 runbook §6.1 的规矩，写成 ASCII 的 `.ps1` 传过去执行，不在命令行里拼 PowerShell。

```
grokgen-wsl-ssh       tcp/2222
grokgen-wsl-comfyui   tcp/8188
```

撤销方法写在脚本注释里（`Remove-NetFirewallHyperVRule -Name grokgen-wsl-ssh`）。
加完三个端口立刻恢复。

⚠️ **什么时候、被什么改成这样的，没有查出来。** 当天早些时候还是好的。
可能是 Windows 更新或睡眠唤醒后重新评估。**这条要写进 runbook**，
因为下次再出现时，症状（连不上）与 §4 那个坑一模一样，但处置完全不同。

## 2. 新增一层验证：提交前预检（VS-14）

**为什么需要它。** `POST /prompt` **没有「只校验不执行」的模式** ——
校验一过任务就排进队列，而 MiniMax H3 加载模型是分钟级的固定开销。
所以「提交一次看报错」这个动作本身不便宜，一次拼写错误要付几分钟。

`app/comfy/workflows/validation.py` 拉一次 `/object_info`，把图对着真实节点定义查：
节点类型存不存在、必填输入给全了没、有没有给未声明的输入、连线指向的节点在不在、
COMBO 的值在不在候选里。

**它需要 ComfyUI 在线，但完全不占 GPU** —— 这是 Level 2 与 Level 3 之间的新一层。

⚠️ **它只查形状，查不了语义。** 两个 VAE 接反、prompt 写错、连到错误的输出槽位，
形状上都是合法的。真正的判据仍然是跑出来的画面。

**第一次跑就抓到了东西**：I2VA / FL2VA 的图各报一条
「`start.png` / `end.png` 不在候选里」—— 那是**真实违例**，
两张图确实还没上传。这正好覆盖了 M1R2 总结里记的「没验证：`LoadImage`
引用的文件名是否真的存在」。

**植入缺陷验证过**：把 `h3_unet` 写成一个不存在的文件名，两条 integration 测试
分别从两个角度报错 —— 预检说「值不在候选里（候选 3 个，如 …）」，
模型存在性检查说「这些模型在服务器上找不到了：[...]」。

## 3. 第一次真实生成

T2VA（不接图，代价最小），`736x416`、5 秒、turbo。

| 步骤 | 结果 |
|---|---|
| `POST /prompt` | `prompt_id` 返回，**`node_errors` 为空**（VS-5 ✅） |
| 执行耗时 | **约 88 秒**（18:50:37 提交 → 18:52:05 完成） |
| 产物 | `output/video/grokgen_00001_.mp4`，505 KB |

⚠️ **88 秒这个读数必须带测量条件**（`Docs/Validation.md` §4.2）：
**模型当时已经在显存里**（ComfyUI 已运行多时，之前跑过 H3）。
冷启动要另加分钟级的模型加载。这个数**不能当作"一次生成要 88 秒"来引用**。

### VS-6：格式（`ffprobe`）

每一项都和 M1R2 的构造精确对上：

| 项 | 实测 | 对应 |
|---|---|---|
| 视频 | `h264` High, `yuv420p` | 不需要转码，架构 §2.4 成立 |
| 音频 | `aac` LC, 32 kHz, 立体声 | 音画合一的 latent 两路解码成功 |
| 容器 | `mp4` | `SaveVideo(format="auto")` |
| 分辨率 | **736x416** | 归一化后的尺寸 |
| 帧数 | **124** | 帧数换算（17k+5 格子） |
| 时长 | **5.167 秒** | `124/24`，与 `actual_duration_seconds` 一致 |

**后三行是对 M1R2 那套换算逻辑的端到端确认** —— 之前只有单元测试说它对。

### VS-7：画面（人眼）

抽了 0.1 s / 2.5 s / 5.0 s 三帧看过：**红色跑车、海岸公路、日落、海浪**，
正是 prompt 描述的内容，不是黑屏也不是噪声。
首尾两帧构图明显不同（车的位置与角度变了），说明有真实的镜头运动，不是静帧。

## 4. 没验证什么

- **画面「好不好」没有判据。** 只判了「不是黑屏/噪声/静帧」。
  8 步够不够、shift 6 合不合适、turbo 的画质损失有多大 —— 都没有对照组。
- **对齐指令行两种写法的差别，仍然无从判定。** 这一轮是 T2VA，根本没有对齐行。
  它要到 M1R4 有首帧时才会出现，而**即便那时也没有便宜的验证方式**。
- **音频内容没听。** 只验了音轨存在、编码是 aac、有 163 帧。
  声音是不是符合 `overall_soundscape` 的描述，没有听。
- **I2VA / FL2VA 没有真跑过。** 预检能过的前提是图片已存在，而上传要到 M1R4。
- **失败路径一次都没走过。** 显存不足、ComfyUI 中途挂掉、任务被取消 —— 都没试过。
  `HttpComfyClient` 的错误分支现在有单元测试（`MockTransport` 喂假响应），
  但**真实的失败长什么样仍然不知道**。
- **`filename_prefix` 写死成 `video/grokgen`**，没按日期分目录。媒体库（M3）要用时再定。

## 5. 哪些验证失败过

轮询脚本第一次解析 `/history` 响应时挂了（`Invalid control character`）——
prompt 里的换行被原样放进 JSON，我那段一行式 Python 没用 `strict=False`。
**是脚本的问题，不是数据的问题**，改用 `json.load(..., strict=False)` 后正常。

## 6. 遗留风险

| 风险 | 说明 |
|---|---|
| 那条防火墙规则为什么会变 | 没查出来。**下次再出现时症状与 runbook §4 一样但处置不同**，已写进 runbook |
| 88 秒是热启动读数 | 冷启动没测过。排期与超时设置不能按这个数来 |
| 对齐指令行两种写法 | M1R4 会用到，但仍然没有便宜的验证方式 |
| turbo 画质 | 没有非 turbo 的对照。真要判断得跑一次 25 步的做对比，那要几分钟 GPU |
