# M1R4 总结：上传与首帧生效

日期：2026-09-22
执行文档：`server/Docs/implementation/M1_gateway_mainline.md` §3 M1R4

**要解决的问题**：首帧图能不能真的生效。
**结论**：生效了，而且不变形。VS-8 通过，新增 VS-15（上传）、VS-16（画布推导）。

---

## 1. Recon 定下的三件事

### 1.1 子目录路径 ComfyUI 官方支持

`LoadImage.INPUT_TYPES` 只列 `input/` 的**顶层**文件，所以子目录里的图
不会出现在候选列表里。但它不影响提交，依据有两层：

* `LoadImage.VALIDATE_INPUTS(s, image)` 只调 `exists_annotated_filepath`，
  即「把名字接在 `input/` 后面看文件在不在」；
* `execution.py:1019` 的
  `if x not in validate_function_inputs and not validate_has_kwargs:` ——
  **COMBO 成员校验只在该输入名不在 `VALIDATE_INPUTS` 参数列表里时才执行**。
  `image` 正好在里面。

⇒ 从源码就能确定，不需要实测。**本轮末尾的实跑也确认了**（`node_errors` 为空）。

⚠️ **但我们自己的预检会误报** —— 这是本轮一个值得记的教训：
**自己造的检查工具会挡住一个合法设计**。放行依据没有硬编码节点名，
而是认 `object_info` 里的 `image_upload: true` 标记（全仓 6 处）。

### 1.2 上传响应不给尺寸，而且会改名

`POST /upload/image` 返回 `{"name", "subfolder", "type", "asset": {...}}`，
**没有 width/height**。

⚠️ **重名会被改名**：不覆盖时 ComfyUI 先比 hash，内容相同就复用，
不同则改成 `name (1).ext`。**必须用响应里的 `name`** ——
用错名字的后果是 workflow 引用到另一张图，**而且不会报错**。
这一条专门写了测试（`test_upload_uses_the_name_comfyui_returned_not_the_one_we_sent`）。

### 1.3 现成的测试素材

`input/example.png` 是 **768x768 的一张涂鸦**（蓝天、白云、绿地、
一个长着黄色蝴蝶翅膀头发的小人）。画风独特，**用来判断首帧是否生效没有含糊余地**；
而且是 1:1，与 16:9 画布的差别一眼可见。它在顶层，**不经过上传就能跑**。

## 2. 契约先改，再动代码

按 `AGENTS.md` §2 的管线，本轮改了 `Docs/contract/gateway_api_v0.1.md`：

* **`asset_id` 变成一个路径**（`grokgen/img_xxx.png`），就是 `LoadImage.image`
  要填的那个值。**不另造 id ↔ 路径的映射** —— M1 没有持久化，
  多一层映射就多一处网关重启后会丢的状态。
* **`width` / `height` 变成可选**：不给且有首帧图时，网关按图片比例推画布。

## 3. 验证了什么

### Level 2（开发机，90 条，不占 GPU）

| VS | 判据 |
|---|---|
| VS-15 | `asset_id` 带 `grokgen/` 前缀；**用 ComfyUI 返回的 name 而不是发过去的**；尺寸从实际落盘路径读；上游挂了是 502 不是 500；读不出尺寸**明确失败而不是回退到猜测值** |
| VS-16 | 1:1 图推出**正方形**画布；常见比例下比例偏差 < 8%；极端比例（16:1）短边不塌成 0；显式给尺寸时**仍然警告会拉伸**；比例本来一致时**不发噪音警告** |
| 预检放行 | 子目录路径不再误报；**但同一张图里别的 COMBO 填错照样报**（防止例外开太大）；缺必填输入照样报 |

⚠️ 「例外不能开太大」那条是反面判据。没有它，把候选检查整个删掉也能让
前两条通过。

### Level 2.5（连 ComfyUI，不占 GPU）

预检对真实 `object_info` 跑通，子目录路径零违例。
另加一条 `ffprobe` 可用性检查 —— **它在开发机上会失败，那是预期的**（开发机没有 ffmpeg）。

### Level 3（占 GPU）—— 分两步走，没有一次验两件事

**第一步：不经过上传。** 用 `input/example.png`（768x768）跑 I2VA，不指定尺寸。

| 项 | 结果 |
|---|---|
| 预检 | 0 违例 |
| 画布 | **544x544** —— 按 1:1 推算，正方形 |
| 产物 | `h264` / 544x544 / 124 帧 |
| 耗时 | 93.8 秒（⚠️ **模型已在显存**，冷启动另算） |

**第二步：真上传。** `POST /v1/uploads/image` 传一张 736x416 的图：

```json
{"asset_id":"grokgen/img_20260922_195609_de30a7.png","width":736,"height":416,"size_bytes":355030}
```

文件确实落在 `input/grokgen/` 下。用这个 `asset_id` 提交，
`node_errors` 为空，产出 736x416（与源图同比例，1.769 vs 1.769），耗时 78.0 秒。

⭐ **这一步同时证明了子目录路径 ComfyUI 真的认** —— 之前只有源码推断。

### Level 4（人眼）—— VS-8 的唯一判据

**第一步的首帧就是那张涂鸦，而且没有变形**：544x544 与原图 768x768 同比例，
人物比例正常。尾帧是明显的推近镜头，涂鸦被渲染成毛毡质感的立体角色 ——
同一个形象、同样的配色，运动真实，不是静帧。

**第二步的首帧就是上传的那张跑车图。**

⇒ 两步都可辨认，**VS-8 通过，没有含糊余地**。

## 4. 没验证什么

- **画布推导的「好看」没有判据。** 只验了比例一致、尺寸合法。
  0.306 MP 这个预算是不是最优、要不要按模型能力调大，没有对照实验。
- **拉伸的反面没有实跑。** 计划里写了「强行给 736x416 跑一次看压扁」作为对照，
  **实际没跑** —— 第一步的正例已经足够判定 VS-8，再花几分钟 GPU 只为看一个
  预期中的坏结果，不划算。⚠️ 所以「不指定尺寸确实避免了变形」这一点，
  严格说是**只验了正面**。
- **FL2VA 一次都没跑过。** 尾帧那条路径至今只有单元测试。
- **对齐指令行两种写法仍无从判定。** 本轮首次真正用到了它（I2VA 会带），
  结果正常 —— 但这只证明**当前写法能用**，证明不了另一种写法**不会更好**。
- **上传的并发与大文件没测。** 只有单张小图。
- **`input/grokgen/` 没有清理机制**，图会一直堆积。

## 5. 哪些验证失败过

`ASPECT_TOLERANCE` 常量第一次没插进源文件（脚本替换的锚点没匹配上），
测试报 `NameError`。**是改文件的方式出错，不是设计有问题**，补上即可。

另一处：`app.include_router` 之后用 `[r.path for r in app.routes]` 查不到新路由，
一度以为没注册。实际是这个 FastAPI 版本用 `_IncludedRouter` 延迟展开，
**是我的检查方式不对**。改用 TestClient 实际调用来确认。

## 6. 遗留风险

| 风险 | 说明 |
|---|---|
| 预检的例外 | 只认 `image_upload` 标记。若 ComfyUI 将来改用别的标记，例外会失效（表现为误报，不是漏报，相对安全） |
| 上传目录无限增长 | `input/grokgen/` 没人清理。M3 媒体库一起处理 |
| `ffprobe` 依赖 | 网关启动时会 warn，但**不阻止启动**。真缺了的话上传会 500 |
| 93.8 / 78.0 秒都是热启动读数 | 冷启动仍未测过 |
