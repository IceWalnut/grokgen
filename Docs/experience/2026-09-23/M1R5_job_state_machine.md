# M1R5：任务状态机与串行队列

**日期**：2026-09-23
**要解决的问题**：显存只够一个重 GPU 任务，两个任务同时提交时必须有人拦住第二个。
**对应判据**：VS-9、VS-10、VS-17、VS-18

---

## 1. 做了什么

### 1.1 主体：`server/app/core/jobs.py`

任务状态机 + 容量为 1 的串行队列，状态存内存（网关重启就丢，M3 再做持久化）。

**串行是结构性的，不是靠计数器。** 用 `asyncio.Queue` 加**一个** worker 协程 ——
「同时跑两个」在这个形状里根本表达不出来。用信号量也能做，但那样 `queued`
这个状态就只是「某个协程阻塞在 acquire 上」，要取消它、要列出它都得额外记账。

**状态转移写成了一张表**（`ALLOWED_TRANSITIONS`），非法转移抛异常。
这是把架构文档 §4 那张图变成一条改坏了会报错的规矩 ——
和 VS-13 把分层约束写成扫 AST 是同一个动作。

表里有两处需要解释的决定：

- **允许 `submitted` 直接跳到 `postprocessing`。** M1 没有 WebSocket，靠轮询观察状态，
  一个短任务完全可能在两次轮询之间跑完，我们根本没机会看到 `running`。
  不允许这条边，**正常路径上**就会抛非法转移。
- **不允许 `postprocessing` 转 `cancelled`。** 走到这一步产物已经出来了，
  取消等于扔掉已经付过的几分钟 GPU。对它的取消请求返回 409。

### 1.2 对外路由：`server/app/api/jobs.py`

`POST /v1/jobs`、`GET /v1/jobs/{id}`、`GET /v1/jobs`、`POST /v1/jobs/{id}/cancel`。

⚠️ **这超出了执行文档原定的「M1R5 只做 core 层」**，是本轮明确决定并已回写执行文档的。
理由：状态机没有入口就只能靠单元测试看，而契约里那几个字段的对齐
本来就要跟着状态机一起定。M1R6 相应缩成「取回产物 + Range」。

### 1.3 ComfyUI 客户端加了三个方法

`queue()`、`interrupt()`、`delete_queued()`。为什么需要它们见第 3 节。

## 2. 本轮最重要的一个发现：seed 会被算两次

**这是一个不会报错的错误，差点写进去。**

`normalize()` 在用户没填 seed 时调 `random.randrange(2**63)` 生成一个随机种子，
而 `build_workflow()` 内部会调 `normalize()`。

原计划是：`POST /v1/jobs` 先算一次 `normalized` 回给 App（契约要求必须回报 seed，
否则用户无法复现），worker 在 `preparing` 阶段再调 `build_workflow` 拼图。

**那会得到两个不同的 seed。** 回报给用户的那个，和真正喂给 `RandomNoise` 节点的
那个不是同一个。任务照样成功，视频照样出来，只是用户拿着回报的 seed
**永远复现不出那个视频** —— 而这不会以任何形式报错。

与 M1R4 踩过的「用错文件名会引用到另一张图且不报错」是同一类事故。

**修法是结构性的，不是加断言**：整条链路只归一化一次。
探测首帧尺寸与建图都在 `POST /v1/jobs` 的请求路径里做完，
结果（`workflow` + `normalized`）存在 `Job` 上带着走，worker 只做预检与提交。

附带好处：图读不出尺寸时在 POST 就返回 400，而不是排了半天队才变成一个失败任务。

VS-18 就是为这条设的，而且**配了一条证明风险真实存在的测试**
（`test_two_normalizations_of_the_same_request_would_disagree`）——
没有它，VS-18 看起来只是在验证一个显然成立的恒等式，
下一个人会觉得「只归一化一次」这个约束是多余的。

## 3. 为什么要给客户端加 `queue()`

**问题**：ComfyUI 的 `/history/{prompt_id}` **只在任务结束后才有记录**，
在排队和执行期间一律返回空。所以光靠它轮询，`running` 这个状态
**任何输入都构造不出来** —— 任务会从 `submitted` 直接跳到完成。

按 `Docs/Validation.md` 的记账规则第三条，一条从未被触发过的分支不算验证过。
而 `running` 不是一个可有可无的状态：App（M2）要靠它区分「已提交、在等」
和「真的在跑」，否则界面上两者长得一模一样，用户会以为卡死了。

**两条独立的理由让这个方法值得加**：

1. **让 `running` 真的可达。** `submitted → running` 由「我的 prompt_id
   出现在正在跑的列表里」推进。
2. **取消的正确性。** 见下。

### 取消有一个必须处理的细节

**ComfyUI 的中断接口没有参数，打掉的是此刻正在跑的那一个，不是按任务 id 取消。**

而这台服务器上 ComfyUI 仍监听 `0.0.0.0`，用户自己也在用它的网页界面提交任务。
不加判断就中断，可能打掉的是用户手工提交的活。

所以取消前先查队列：

| 那个任务在哪 | 怎么做 |
|---|---|
| 正在跑 | 发中断 |
| 还在 ComfyUI 队列里排着 | **从队列删掉它**，不能发中断（那会打掉排在前面的、别人的任务） |
| 两个列表里都没有 | 它已经跑完了，下一轮轮询会拿到记录，交给那里判定 |

`delete_queued()` 就是为第二种情形加的。串行队列下网关一次只提交一个，
所以这一支只有在「ComfyUI 队列里有别人的任务」时才可达 ——
但那个状态是真实的，而没有这个方法，这一支就只剩
「打断别人」和「什么都不做、让它跑成孤儿产物」两个都不对的选项。

## 4. 验证了什么

### Level 2（开发机，不占 GPU、不连服务器）

```bash
cd server && .venv/bin/python -m pytest -m "not integration"
# 130 passed, 5 deselected
```

本轮前是 90 条，新增 40 条。**原有 90 条一条没破。**

#### VS-9 —— 串行队列

判据原文是「连续提交 3 个任务，**任何时刻**只有一个处于 `submitted`/`running`」。

「任何时刻」不能靠采样几次去看 —— 那是碰运气。这里用的是**回放整条转移日志**：

> 任务状态是**分段常数**的，只在转移点改变。
> 所以「在每个转移之后取一次快照的最大值」与「对连续时间取上确界」是同一个数。
> 这不是抽样，是完备的。

`peak_gpu_occupancy()` 就是这个回放函数，断言它等于 1。

**三条互相独立的断言，抓的是不同的失败模式**：

1. **回放日志算峰值** —— 抓「状态重叠」；
2. **替身在提交边界上自己守的那道**（`FakeComfyClient` 的 `serial_guard`）——
   抓「worker 被并发起了两份」。它的价值在于**不依赖网关自己的记账**：
   即使网关的转移日志写错了，越界提交也会在这个边界上炸；
3. **提交顺序** —— 这是**正向的数**。前两条都是负向的：
   一个三个任务全卡在 `queued`、一个都没跑的队列也能让它们通过。
   所以必须断言三个 `submitted` 转移确实都发生了，且顺序就是提交顺序。

还加了一条**守判据本身**的测试：喂 `peak_gpu_occupancy` 一条重叠的日志，
它必须报 2。没有这条，一个恒返回 0 的实现也能让 VS-9 变绿 ——
那就是一条永远不会失败的判据。

**⭐ 植入缺陷验证过会红。** 把 worker 从 `await self._run_one(job)` 改成
`asyncio.create_task(self._run_one(job))`（即并发而非串行）后：

```
FAILED test_three_jobs_never_occupy_the_gpu_at_the_same_time
  AssertionError: job_20260923_0001 占着 GPU 时，其余任务的状态是 [preparing, preparing]
FAILED test_cancelling_a_queued_job_never_touches_comfyui
  AssertionError: 上一个任务还没结束就又提交了一个：仍未结束的是 ['fake-prompt-0000']
```

报出的是具体哪个任务在什么状态，不是一个语焉不详的失败。已改回。

#### VS-10 —— 失败原因带得回来

断言的是 `failure_reason.detail` 与喂进去的 `node_errors` **逐字段相等**，
不是「detail 不为空」—— 把它压成一句字符串也能让「不为空」通过，
而那恰恰是这条判据要防的事。另外正向确认了那条具体信息
（`{"2": {"errors": [{"details": "channels"}]}}` 里的 `channels`）还在，
没有在传递过程中被摊平。

**⭐ 植入缺陷验证过会红。** 把 `detail=exc.node_errors` 改成
`detail=str(exc.node_errors)` 后这条立刻失败。已改回。

失败分类另外测了三条：连不上（`comfy_unreachable`）、显存不足（`out_of_memory`）、
认不出类别的（`internal`，但消息原文同样保留）。

#### VS-17 —— 取消的三种情形

- 排队中取消：**正向断言「一次 ComfyUI 调用都没发生」**
  （`interrupts == 0` 且 `deleted_from_queue == []` 且 `prompt_id is None`）。
  只断言状态变成 `cancelled` 的话，一个「先通知 ComfyUI 再取消」的错误实现
  也能通过，而那会白白打断别人的任务。
- 运行中取消：确认真的发了中断，终态是 `cancelled`。
- **正在跑的不是我们那个时，不许发中断** —— 这组里最重要的一条，
  构造方式是让替身报告「正在跑的是另一个 prompt_id」（模拟用户手工提交的）。
- 终态取消：抛 `JobAlreadyFinished`，HTTP 层 409。
- **取消与完成的竞态**：取消晚了一步、任务已经成功了，
  产物必须保住，不能把一个已经存在的视频标成取消。

#### VS-18 —— seed 只算一次

见第 2 节。

#### 其余

状态机本身（终态不再变化、每个非终态都能转 failed、允许 submitted 直跳
postprocessing）、预检拦下的图**正向断言没被提交出去**（`comfy.submitted == []`）、
超时分支、默认不超时、列表倒序、关停后拒收新任务。

HTTP 层 11 条：契约字段名（**用原始 JSON 发请求**，因为 `first_frame_asset_id`
是靠别名映射的，别名断了只有走 JSON 才会暴露）、九个 normalized 字段齐全、
`stage`/`progress` 明确为 null、列表的 `items`/`total`/过滤/limit 边界、
404 / 409 / 422。

## 5. 没验证什么

**这一节不是可选项。** 以下都是本轮结束时只有替身证据、或完全没有证据的部分。

### 5.1 `running` 状态在真实链路上是否可达 —— 没验证

`/queue` 的解析在 Level 2.5 有「能连上、能解析」的证据，但**当时队列是空的**。
所以「prompt_id 取的是条目的下标 1」这个假设，**只有替身证据**。
取错槽位不会报错，只会让「任务开始跑了没」这个判断永远为假 ——
表现为任务卡在 `submitted`，而不是一个明确的错误。

**补证时点已经定了**：M1R7 冒烟时本来就要真跑一次生成，
在那里加一条判据「轮询期间至少观察到一次 `state == running`」。

### 5.2 `interrupt()` 真的能中断一次 H3 生成 —— 没验证

这是本轮**最薄弱的一处**。`httpx.MockTransport` 只证明请求发对了路径。

「被中断的任务在 `/history` 里那条记录长什么样、`status_str` 是什么」
完全是推的 —— 代码里 `record.status != "success"` 那条判定**没有任何真实证据**。
补证要占 GPU（提交一个真任务再取消它），属于 Level 3，本轮不做。

### 5.3 `delete_queued()` 一次都没真跑过

它只在「ComfyUI 队列里有别人的任务排在前面」时才可达，
而那要手工在浏览器里提交才会出现。按记账规则第一条：
它**构造得出来**（手工提交两个再取消），但要占 GPU。本轮记成未验证。

### 5.4 超时分支在生产里零证据

默认 `None` 意味着它永远不触发；测试里靠 `timeout_seconds=0.01` 构造。
所以「网关会在合适的时候杀掉一个卡死的真实任务」这件事本轮没有任何证据 ——
而这恰恰是把它默认关掉的理由：没有依据的秒数，误杀一次就是几分钟 GPU。

### 5.5 `stage` 与 `progress` 恒为空

M1 没有 WebSocket，**任何输入都构造不出非空值**。
按记账规则第一条，这种情况**不补构造用例**，只在代码注释和契约里
写明「M2 接 ws 后才可达」。

### 5.6 显存不足的分类依据是猜的

`_looks_like_out_of_memory()` 是字符串匹配，依据是 PyTorch 的 OOM 文案，
**没有一条真实的 ComfyUI OOM 消息作样本**。
替身测试只证明「给了含这个字样的消息会分类成 out_of_memory」，
证不了真实 OOM 的消息长这样。认错的后果是降级成 `internal`
（一个更笼统但不算错的分类），不会把失败伪装成成功。

### 5.7 串行行为没在真机上验过

真实验证要连跑 3 次生成，按 M1R3/M1R4 的热启动读数每次约 80–95 秒。
本轮的判据本来就定成纯逻辑层。**不要因为 VS-9 通过了就以为
串行已经在真机上验过。**

### 5.8 网关本身没有部署到服务器

本轮改完没有跑 `deploy_server.sh`，所以新路由在服务器上一次都没起来过。

## 6. 哪些验证失败过

**一处真失败，是命名问题。**

`JobManager` 里原本有个方法叫 `list`。它在类作用域里遮蔽了内置的 `list`，
导致同一个类里后续的 `-> list[Transition]` 注解解析到了那个方法上，
报出的是：

```
TypeError: 'function' object is not subscriptable
```

**这个报错和真实原因毫无关系**，指向的行也不是出问题的那一行。
改名成 `list_jobs` 后正常，并在 docstring 里写明了为什么不能叫 `list`。

另外两次「失败」是故意的（植入缺陷验证判据会红），见第 4 节。

## 7. 下一轮遗留的风险

| 风险 | 说明 |
|---|---|
| `job_id` 序号会重复 | 序号是**进程内**的，网关重启后从 0001 重来，同一天重启两次就会产生重复 id。M1 状态不持久化、重启后旧 id 本来也查不到，所以现在影响为零 —— 但 **M3 做持久化时必须先解决它**，否则会撞主键 |
| 关停会丢状态但不丢产物 | 网关关停时**不中断**已提交的任务（一次生成是分钟级 GPU 开销，为了状态干净扔掉它是亏的）。产物照样落到 `output/`，但网关侧状态丢失。日志里留了 `prompt_id`，那是重启后找回产物的唯一线索 |
| `interrupt` 的落地形式没验证 | 见 §5.2。这是最该在 M1R7 补上的一条 |
| ComfyUI 仍监听 0.0.0.0 | 取消逻辑里那三个分支的存在理由就是它。收回到只监听回环之后，「队列里有别人的任务」这个状态才会消失 |
