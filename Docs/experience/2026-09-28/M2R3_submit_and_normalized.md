## 2. VS-34：golden 为什么必须用线上那个 `Json`，以及三次植入

### 2.1 序列化的坑是真的

kotlinx.serialization 默认 `encodeDefaults = false`：**带默认值的属性等于默认值时直接从 JSON 里省略**。
所以请求数据类里写 `val width: Int? = null`，发出去的是「没有 width 这个键」，
不是契约写的 `"width": null`。网关恰好把缺省当 null 处理，**今天不会出错**，
但那是巧合，不是约定。

**做法**：`JobSubmitRequestDto` 的属性**一律不给默认值**；
`GatewayClient` 里的 `Json` 提成 `net/GatewayJson.kt`，**线上与测试共用同一个实例** ——
测试自己 new 一个的话，测试是绿的、线上发出去的却可能是另一个形状。

### 2.2 三次植入，各自变红

命令：`JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 ./gradlew testDebugUnitTest --tests '*SubmitRequestGoldenTest*'`（在 `app/` 下）

| 植入的缺陷 | 结果 |
|---|---|
| `JobSubmitRequestDto.width` 改成 `Int? = null` | 3 条全红，报「缺少键 width」 |
| `GatewayJson` 加 `explicitNulls = false` | 3 条全红，报缺少 `width`/`height`/`steps`/`last_frame_asset_id`/`seed`/`first_frame_asset_id` |
| `toSubmitRequest` 在文生视频模式下照样带首帧图 | 只有文生视频那条红，报 `first_frame_asset_id` 应为 null、实际是那张图的 asset_id |

三处都已改回，全部测试恢复通过。

### 2.3 跨端核对（一次性，不进仓库）

pydantic 会**静默丢掉**没声明的字段，所以「网关能解析」查不出 App 多发了字段。
用 `server/.venv/bin/python` 对三份 golden 各做两件事：
`VideoJobRequest.model_validate` 能过；
**golden 的键集合 == `VideoJobRequest.model_fields` 按 alias 换算后的 12 个键**。三份都是 `True`。

## 3. VS-35：真机上看到的

操作：连接页 → 去生成视频 → 选择首帧图 → 上传一张 1080×1352 的 JPEG →
用这张图做首帧 → 填画面描述（英文，`adb input text` 打不了中文）→ 5 秒 / Turbo / 种子随机 → 生成视频。

界面显示（截图 `shots/r3-03`）与网关 `GET /v1/jobs` 返回的逐项一致：

| 显示项 | 值 | 说明 |
|---|---|---|
| 分辨率 | 480 × 608 | **竖图推出竖画布**，网关按首帧图比例推的（notice 原文也说了） |
| 时长 | 5.17 秒 · 124 帧 | 网关回报的是未取整的 5.1666…，App 保留两位 |
| 种子 | 7288075759306197 | 网关生成（< 2^53，网关的 `MAX_SAFE_SEED`） |
| 采样 | euler · 8 步 · Turbo | |
| shift | 6.0 / 3.0 | |

两条 notice 原文显示，未按前缀解析。网关上只有这一个任务 —— **没有重复提交**。

### 3.1 顺带的一个耗时读数

提交 05:58:08（UTC）→ 产物文件写出 05:59:43，**约 95 秒**，不是热启动的 75 秒。
原因看得到：提交前连接页显示显存 **1.3 GB / 16.0 GB 已用**，跑完是 **14.7 GB** ——
提交时模型不在显存里。这与 ContextPack §4.31 里「显存清空后重载 94 秒」一致。
⚠️ **只有 1 次**，而且画布是 480×608，和以前的 736×416 不是同一个输入。

## 4. 做的时候发现的，按影响排

### 4.1 ⭐ 3 秒这一档低于模型训练过的帧数范围 → 改成 5 / 8 / 10

最初和用户定的是 3 / 5 / 8 秒。读网关代码发现 `TRAINED_FRAME_RANGE = (124, 362)` 帧，
24 fps 下约 5.17–15.1 秒。**3 秒换算后是 73 帧，低于范围** ——
网关照样生成，但会附一条「超出训练范围，结果可能不稳定」的 notice。
用户确认后改成 **5 / 8 / 10**（124 / 192 / 243 帧，都在范围内）。
⚠️ **8、10 秒显存够不够没有实测过**。

### 4.2 ⭐ 超时一律当「不确定是否已提交」

提交有副作用：重复一次 = 多一个任务、多付一次 GPU。
OkHttp 的连接超时和读超时抛的都是 `SocketTimeoutException`，只能靠消息文字区分，那很脆弱。
而分错的代价不对称：把「没连上」说成「不确定」，用户多看一眼队列；
把「已登记但响应丢了」说成「没连上」，用户重复提交。
⇒ **任何超时都归 `SubmitOutcome.MaybeSubmitted`**，文案引导用户先确认队列。
`UnknownHostException` / `ConnectException` 才归「确定没发出去」。
⚠️ 这条**没有在真机上触发过**（要制造一个请求到了网关、响应却丢了的情况）。

### 4.3 网关不拦「I2VA 却没带首帧图」

读 `server/app/api/jobs.py`：`first_frame` 为空就不探测尺寸，直接拼图 ——
I2VA 不带图会照常生成一个不带图的视频，**不报错**。
按用户决定**只在 App 端拦**（按钮不可点 + `toSubmitRequest` 的 `require`），网关的漏洞记进 TODO。

### 4.4 网关响应的 `normalized` 比契约多一个 `notices`

契约 §2 的示例是 9 个字段；网关的 `NormalizedParams` 模型里带着 `notices`，
所以实际返回 10 个键（外层那份相同）。App 靠 `ignoreUnknownKeys` 忽略，
`NormalizedSummaryTest` 用带着它的真实形状守着。**契约本轮未改**。

### 4.5 构建要显式指定 JDK 17

直接 `./gradlew` 会用系统默认的 Java 11，AGP 报「requires Java 17」直接失败。
`build.gradle.kts` 里的 `jvmToolchain(17)` 管的是编译，**管不了跑 Gradle 本身的那个 JVM**。
要写成 `JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 ./gradlew ...`。
以前的文档里没写这条，本轮补进了根 `README.md` 与 M2 执行文档 §4.4。

### 4.6 `./gradlew test --tests` 不认

`test` 是聚合任务，不接受 `--tests`；要用 `testDebugUnitTest --tests '...'`。

## 5. 真机上看出的一处视觉问题，已修

上传成功后，「上传」和新加的「用这张图做首帧」**两个强调色按钮并排**，抢主次（`shots/r3-04`）。
改成上传成功后「上传」禁用变灰 —— 同一张图再传一次只会在服务器上多一份；
重新选图会重置状态，按钮随之恢复。重装后真机确认（`shots/r3-05`）。
