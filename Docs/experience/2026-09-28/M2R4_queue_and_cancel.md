## 2. 三条判据是怎么验的

### 2.1 VS-36：数网关日志里的请求

网关的 uvicorn 访问日志每个请求一行（**不带时间戳**），所以做法是「数两次行数，看中间涨没涨」。

| 场景 | 读数 | 结论 |
|---|---|---|
| 停在一个**已取消**任务的详情页 12 秒 | 取消后只有 1 次 `GET`，之后没有 | 终态即停 ✅ |
| 按 Home 键 **3 秒后**开始数，后台 30 秒 | 12 → 12 | 后台不轮询 ✅ |
| 回到前台 6 秒 | 12 → 13 | 恢复轮询；任务已在后台期间结束，**问 1 次拿到 `done` 就停了** ✅ |
| 断网恢复、任务 `done` 之后 15 秒 | 8 → 8 | 终态即停 ✅ |

⚠️ **第一次测后台时读数不干净**：先读行数、再按 Home，后台 30 秒里涨了 1（3 → 4）。
推测是读数到按 Home 之间那 1〜2 秒里正好轮询了一次（间隔 2 秒）。
**改成「按 Home → 等 3 秒 → 再开始数」之后是 12 → 12。** 两次都如实记在这里。

Level 2 的证据是 `JobPollerTest`：等待函数被换成「立刻返回、记下时长」，
断言「第 N 次到终态恰好问 N 次」「取消收集后请求数不再涨」「退避序列 2、4、8、2 秒」。

**植入缺陷验证过会红**：把「到终态就结束」改成永不结束 → 3 条变红，
报「剧本只有 N 步，却被问了第 N+1 次 —— 该停的时候没停」。
（为此把假查询改成**剧本用完还被调就直接失败**，否则「该停没停」会表现为测试挂死。）

### 2.2 VS-37：取消

- **排队中取消**：连续提交两个任务，取消排着的那个 → `cancelled`；
  ComfyUI 的队列里只有第一个任务的 workflow，**第二个从没被送去 GPU**。
- **运行中取消**：运行约 40 秒时点两下取消 → 截到了中间态「正在取消…」（`shots/r4-05`），
  随后变「已取消」；ComfyUI 队列清空。**这证实了契约更正的那条：取消运行中的任务是异步的。**
- **对终态取消返回 409**：界面上任务结束后取消按钮就隐藏了，自然触发不了。
  用 `curl -X POST .../job_20260928_0001/cancel` 对一个 `done` 任务确认网关返回
  `409 {"detail":"任务 job_20260928_0001 已经结束或正在收尾，不能取消"}`；
  App 那一侧由 `JobQueryOutcomeTest` 守（409 → `AlreadyFinished`，植入缺陷验证过会红）。
  **所以这一档是 Level 2 + curl，没有在真机界面上验过。**

### 2.3 VS-38：断网

任务运行约 30 秒时 `adb shell am force-stop com.tailscale.ipn`（手机上的 VPN 随之断开）：

- 25 秒后界面：顶部「连接中断，重试中 —— 任务在服务器上照常跑，不受影响。手机没连上 Tailscale。」，
  状态卡**保留上一次的「生成中」**，不是失败（`shots/r4-07`）；网关那边任务照常 `running`。
- 重新打开 Tailscale、切回 App → 「完成」（`shots/r4-08`）。

⚠️ **恢复走的是「回到前台重新开始」那条路，不是退避重试那条路**：
打开 Tailscale 时 grokgen 被切到了后台，轮询按设计停了；切回前台立刻重查。
退避序列本身只有单元测试的证据，**没有在真机上观察到 4 秒、8 秒的间隔**。

## 3. ⭐ 真机上抓到的网关 bug：取消排队任务会刷一段 traceback

**现象**：取消了一个排队中的任务之后，网关日志里出现：

```
任务 job_20260928_0002 的执行过程抛出了未预期的异常
app.core.jobs.InvalidTransition: job_20260928_0002: cancelled → cancelled 不是合法转移
```

**根因**：`cancel()` 对排队中的任务直接落 `cancelled`（注释写着「worker 取出来时会跳过」），
而 `_run_one` 取到它时**并没有跳过**，又 `_set_state(CANCELLED)` 一次 —— 非法转移，抛异常。

**影响**：功能没坏 —— worker 兜住了异常继续跑（同时段的第一个任务正常完成），
任务本来就是终态也没被改成失败。但**每取消一次排队任务就刷一段 traceback**，
真正的错误会淹没在里面。

**为什么以前的测试没抓到**：`test_cancelling_a_queued_job_never_touches_comfyui` 等第一个任务完成
就关掉了管理器，**worker 根本没走到第二个任务**；而且即便走到了，异常被兜住只写日志，那条测试也不看日志。

**修法**：`_run_one` 里已是终态就直接返回。新测试**提交第三个任务逼 worker 越过被取消的那个**，
再断言日志里没有 ERROR —— 修复前红，修复后绿。重新部署后又做了一次排队取消，日志里 0 条 traceback。

⚠️ 这和 ContextPack §4.011 那条教训是同一个家族，但换了个样子：
**不是替身演得不对，而是测试没把流程走到底、也没看「被兜住的失败」落在哪。**
被 `except Exception` 兜住的错误，测试只看状态是看不见的。

## 4. 其他发现，按影响排

### 4.1 ⭐ 进度数据只能来自 ComfyUI 的 WebSocket —— 已核实

读了服务器上 ComfyUI（`3c80da7f`，2026-09-18）的源码。它新增了 `/api/jobs`、`/api/jobs/{id}`，
但返回的只有 `id` / `status` / `create_time` / 输出数量等，**没有进度、没有当前节点**；
步数进度只在 `progress` 事件里（`main.py`），当前节点只在 `executing` 事件里（`execution.py`）。
⇒ App 架构文档 §12 那一行从「未核实」改为「已核实」。网关连 WebSocket 另开一轮（TODO）。

顺带看到：ComfyUI 的 `/api/jobs/{id}/cancel` 用 `interrupt_if_running(prompt_id)`
**原子地**只中断指定任务 —— 网关现在是「先查正在跑的是不是它、再发无参数的 `/interrupt`」，
两步之间有竞态。**现在影响为零**（只有一个用户），记进 TODO，下次动取消逻辑时考虑换用。

### 4.2 ⭐ 协程取消不能被当成「连不上」吞掉

App 退到后台时，收集轮询的协程被取消，**正在进行的请求会抛 `CancellationException`**。
`JobClient` 若像 `ImageUploader` / `JobSubmitter` 那样 `catch (Throwable)`，
就会把它归成「连不上」—— 后台不轮询那条会悄悄失效。
`JobClient` 已改成先原样抛出 `CancellationException`，并有一条专门的测试。
⚠️ **`ImageUploader` 与 `JobSubmitter` 仍是 `catch (Throwable)`**：它们不在轮询循环里，
影响小得多（最坏是页面销毁时多一次无人看的状态更新），但写法是同一个坑，记进 TODO。

### 4.3 ⚠️ 仓库里的截图让每次部署变慢，还造成了一次误诊

部署时服务器上的 `git fetch` 看起来「卡住了」5 分多钟，我把它杀了。
实际是**在慢慢下载一个 14 MB 的 pack**（13,986,027 字节）：M2R2、M2R3 提交的 PNG 截图都在里面，
而服务器到 GitHub 只有每秒几十 KB。杀掉的两次各留下约 11〜12 MB 的临时 pack（`tmp_pack_*`，
共约 23 MB，`git gc` 会清掉，本轮没动）。
最后用 `setsid nohup git fetch` 在服务器后台跑完，再部署。

⇒ **服务器只需要 `server/`，却要下载整个仓库的历史，包括所有截图。**
每轮都往仓库里加截图，这个代价会越来越大。解决办法（浅克隆、sparse checkout、截图不进仓库）
**本轮没定**，记进 TODO。⚠️ 部署脚本对 `git fetch` 没有超时，也没有进度输出 —— 慢和卡分不开。

### 4.4 契约与实现的几处出入，本轮都已改契约

- 取消运行中的任务：契约写「变 `cancelled`」，实际返回时可能还是 `running`（异步）；
- 取消接口还会返回 **502**（网关连不上 ComfyUI）；`postprocessing` 取消返回 **409**；
- 列表默认 `limit`：契约写 50，实现是 20；列表响应带 `total`，契约原来没写。

M2R3 记下的那条（`normalized` 里多一个 `notices`）**本轮没动**，仍在 TODO。

### 4.5 真机上看出的一处文案问题，已修

排队中的任务点取消，确认提示写着「已经跑掉的时间不会退回」—— 它还没跑过。
改成按状态区分：生成中说「已经跑掉的时间不会退回」，排队中说「它还没开始跑，取消不浪费什么」。
`shots/r4-02` 是修正前的样子。

## 5. 设计上做了的决定

- **轮询跟着界面的收集走**：ViewModel 用 `stateIn(WhileSubscribed(0))`，界面用
  `collectAsStateWithLifecycle`。退到后台 = 收集取消 = 轮询停，**没有另写一套暂停逻辑**。
  用 `0` 而不是常见的 5 秒宽限，是因为 VS-36 要求退到后台就停；代价是转屏时会立刻重查一次。
- **认不出的 `state` 不当终态**：原样显示「未知状态：xxx」并继续查询 —— 终态判断是白名单。
- **取消是两步确认**：运行中的任务一旦取消，已付出的 GPU 时间就白费了。
- **详情页不猜 Turbo**：`summarizeNormalized` 的 `turbo` 改成可空，从详情进来时只显示「euler · 8 步」，
  不按步数去猜档位（那等于在 App 里再抄一份网关的采样档位规则）。
- **仍然不引导航库**：五个页面、只有详情页要带一个字符串参数；详情一律回队列。理由写在 `MainActivity` 里。

- **409 那一档没有在真机界面上触发过**（§2.2）

- **很长的 prompt、很多条任务**时的排版没看；横屏没看
- **失败任务的详情**（失败原因卡片、展开原始信息）没在真机上见过 —— 这一轮没有任务失败
- **M1 的退出标准仍未收尾** —— 「手机上能播」是 M2R5
