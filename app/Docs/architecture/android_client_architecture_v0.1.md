## 1. 最重要的一个决定：进度用 App 轮询，不做服务端推送

**结论：M2 的 App 用轮询 `GET /v1/jobs/{job_id}` 获取任务状态与进度，
网关不向 App 推送。** 契约 §6 那个 `WS /v1/events` 在 M2 **不实现**。

### 1.1 这里其实是两段链路，别混在一起

| 链路 | M2 怎么做 |
|---|---|
| 网关 ↔ ComfyUI（上游） | 网关连 ComfyUI 的 WebSocket 拿实时进度，**这一段照做** |
| 网关 ↔ App（下游） | **App 轮询，不推送** |

⚠️ **这两件事要分开决定。** 契约里的 `stage`（现在是加载模型还是采样）
和 `progress`（采样百分比）这两个字段，数据**只能**来自 ComfyUI 的 WebSocket 事件 ——
网关现在调用的两个 ComfyUI 接口（`/queue` 问「队列里有哪些任务」、
`/history/{id}` 问「这个任务的最终结果」）**都回答不了「现在跑到第几步」**。

所以「下游不推送」**不等于**「上游也不连 ws」。
把上游那段一起砍掉的话，`stage` 会永远是空的，
而需求 F2 明确要求把 `loading_model` 这一段单独显示出来。

⚠️ **「网关这一侧必须连 ComfyUI 的 ws 才拿得到 stage」这一条还没有核实过** ——
它是从网关目前已实现的三个 ComfyUI 接口推出来的，
没有去 ComfyUI 源码里确认是否存在别的 HTTP 途径。M2 开工时先确认一次（§12）。

### 1.2 为什么下游选轮询

推送方案买到的通常是两样东西：**减轻服务端被 N 个客户端轮询的压力**，
以及**亚秒级的状态延迟**。在这个项目里这两样都等于零。

**并发压力为零**：只有一个用户、一台手机。轮询的服务端成本是
「客户端数 × 频率」，客户端数是 1。

**延迟优势也几乎为零，这条是决定性的。** 按 M1R7 的实测配置
（736x416 分辨率、124 帧、8 步 Turbo 采样，各测 1 次），
一次 5 秒视频热启动约 75 秒。**采样只有 8 步**，
意味着整个采样阶段能产生的进度更新最多 8 次，平均每 9 秒一次。
而 App 每 2 秒轮询一次，75 秒里能问到约 37 次 ——
**轮询的采样密度已经是进度事件密度的 4 倍以上，推送没有多出来的信息可以给。**

⚠️ 「ComfyUI 每个采样步推一个进度事件」是常规行为，**没有在这台服务器上抓包确认过**。
即使实际是每两步一次或每秒一次，结论方向不变（仍远稀于 2 秒一次的轮询）。

**轮询还额外买到一样东西**：每次 `GET /v1/jobs/{job_id}` 返回的是
**完整的当前状态**，所以漏掉一次请求会被下一次自动补上。
推送是增量的，掉一条事件就少一次状态转移，除非再加序号与补发。
手机上切 Wi-Fi/移动网络、App 退到后台、系统省电限制都会掐断长连接 ——
**推送方案在手机上必须再写一套轮询兜底，而这里那套兜底本身就够用了。**

### 1.3 将来真要推送时走哪条路

**先看 SSE（Server-Sent Events），不要直接上 WebSocket。**
SSE 是单向的、走普通 HTTP、FastAPI 原生支持，不引入第二种传输协议。
WebSocket 的双向能力在这里用不上 —— 提交任务和取消任务都已经是 REST 接口，
App 没有任何需要通过长连接往上发的东西。**用 ws 属于选了一个比需求大一号的方案。**

契约 §6 的位置和「断线时 App 退回轮询」那句保留，但标成 M2 不做。

## 2. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Kotlin | Android 的默认，官方文档与库都以它为准 |
| UI | Jetpack Compose | 页面少、状态驱动强（任务状态每 2 秒变一次），Compose 的重组模型正好 |
| 网络 | OkHttp + Retrofit + kotlinx.serialization | 见下 |
| 播放 | **AndroidX Media3（ExoPlayer）** | 见 §9，这是 M2 退出标准的核心依赖 |
| 本地存储 | DataStore Preferences | 只存一个后端地址，不需要数据库 |
| 依赖注入 | **不用框架，手工装配** | 见下 |
| 异步 | Kotlin 协程 + `StateFlow` | 轮询循环天然是协程 |
| 编译目标 | compileSdk / targetSdk **36**，minSdk **26** | 开发机装的是 `android-26` 与 `android-36`（`AGENTS.md` §4），不额外下载平台 |
| JDK | 17，通过 Gradle toolchain 声明 | 系统默认 `java` 是 11 且**不要动它**（`AGENTS.md` §4） |

⚠️ **具体的库版本号本文档不写。** 版本在 M2R1 第一次真正构建成功时才确定，
写在 `app/gradle/libs.versions.toml` 里。
**在这里写一个没构建过的版本号，是把一条未验证的事实放进架构文档。**

**为什么用 Retrofit 而不是裸 OkHttp**：接口有九个（任务五个、上传一个、
健康检查一个，媒体库与 GPU 留给 M3/M4），手写请求构造和错误分支会重复九遍。
Retrofit 的价值在于**把 HTTP 状态码映射成类型化结果**这件事只写一次 ——
而契约里 409（还没好，继续等）和 404（不存在，别再问了）是必须分开处理的，
混成一个 App 就不知道要不要继续轮询。

**为什么不用 Hilt/Koin**：整个 App 只有一个需要注入的东西（配好地址的
`GatewayApi` 实例），而它的构造依赖一个运行时才知道的值（用户填的服务器地址）。
依赖注入框架在这种"依赖在运行时变化"的场景里反而要额外写作用域管理。
手工装配放在一个 `AppContainer` 类里，**十几行，且可以直接在单元测试里换掉**。

⚠️ **这条选择的代价要认**：App 长大到 M4（加上 SD 生图页、GPU 页、媒体库页）时，
手工装配可能会变难看。**那时再引入框架**，不要现在为了将来付复杂度。

## 3. 分层，以及唯一的硬约束

```text
app/src/main/java/com/icewalnut/grokgen/
├── MainActivity.kt          Compose 宿主 + 导航
├── AppContainer.kt          手工装配，唯一知道怎么拼出 GatewayApi 的地方
├── net/                     ★ 唯一允许说 HTTP 的层
│   ├── GatewayApi.kt        Retrofit 接口声明，一比一对应契约
│   ├── dto/                 请求/响应的数据类，字段名与契约逐字对应
│   ├── GatewayClient.kt     OkHttp 装配、超时、日志
│   ├── ServerAddress.kt     ★ 唯一允许出现服务器地址字面量的文件
│   └── ConnectionOutcome.kt 把异常与响应体翻译成四种结果（§5）
├── data/
│   ├── SettingsStore.kt     DataStore：后端地址
│   ├── JobRepository.kt     任务的取用与轮询循环（§7）
│   └── UploadRepository.kt  相册图 → multipart 上传（§8）
├── ui/
│   ├── theme/               ★ 唯一允许出现颜色字面量的包（§9.5）
│   ├── component/           跨页面共用的组件（如 JobStatusChip）
│   ├── connect/             F1 连接页
│   ├── generate/            F2 视频生成页
│   ├── queue/               F4 队列页 + 任务详情
│   └── player/              视频播放（§9）
└── model/                   UI 用的领域模型，与 net/dto 分开
```

### 3.1 唯一的硬约束（可执行，不是口号）

> **除 `net/` 包以外，任何源文件都不许 import HTTP 库；
> 除 `net/ServerAddress.kt` 以外，任何源文件都不许出现服务器地址或端口的字符串字面量。**

这条**要写成一个跑得起来的单元测试**（落在 `app/src/test/.../SourceConstraintsTest.kt`，
与 §9.5.4 的颜色约束合在同一个文件里）：
扫 `app/src/main/java` 下每个 `.kt` 文件，
断言 `okhttp3` / `retrofit2` / `java.net.HttpURLConnection` 的 import
只出现在 `net/` 下，且 `tail22a711` / `ts.net` / `:7869` / `100.64.` 这些字面量
只出现在 `ServerAddress.kt` 里。

⭐ **M2R1 已落地并植入缺陷验证过**：三条各自变红一次，报出具体文件与行号。

⚠️ **为什么要有这条**：网关侧有一条完全对称的约束（`VS-13`，
落在 `server/tests/test_layering.py`），它的价值在 M1 里被证明过 ——
判据写成"扫源码"而不是"测试能跑通"，违例时报的是**具体哪个文件的哪一行**。

⚠️ **判据必须是扫源码，不能是「不连服务器时测试全通过」。**
后者是个消极判据：有人在 `ui/` 里直接发了个请求而测试恰好没走到那条路，它照样是绿的。

⚠️ **写死地址这条对 App 比对网关更重要。** 网关写死了地址，改一行重新部署即可；
**App 写死了地址，已经装在手机上的那个版本就永远连的是旧地址** ——
而 Tailscale IP 在设备重装后会变（runbook §2）。

### 3.2 `model/` 和 `net/dto/` 为什么要分开

契约里的字段有些是 M1 恒为空的（`stage`、`progress`）、
有些是目标形状而非当前返回（`outputs` 里的 `item_id` / `codec` / `size_bytes`，
见契约 §2 的警告）。**UI 不应该直接消费这种"有时有有时没有"的形状。**

`net/dto` 逐字对应契约（包括 `null`），`model/` 是 UI 真正要显示的东西，
中间一层映射函数负责决定"字段为空时 UI 显示什么"。
**那个决定写在一个地方，而不是散在每个 Composable 里的 `?: "未知"`。**

## 4. 页面与 M2 的范围

| 页面 | 需求 | M2 做到什么程度 |
|---|---|---|
| 连接页 | F1 | 填后端地址、显示是否可达、**连不上时区分几种原因**（§5，实测是四种可区分的结果）。**GPU 状态与服务切换按钮不做**（那是 M4 的 `GET /v1/gpu`，契约 §5 仍是草案） |
| 视频生成页 | F2 | 模式 T2VA / I2VA、三段 prompt、时长、turbo 开关、seed、提交。**FL2VA（尾帧）不做**、**LoRA 不做**（M6）、**高级参数不做** |
| 队列页 | F4 | 任务列表、当前状态、取消。**重跑、复制参数、日志摘要不做** |
| 任务详情 | F2 / F4 | 状态、`normalized` 九个字段、`notices`、失败原因、播放入口 |
| 播放 | §6 | Media3 播放 `GET /v1/jobs/{id}/video`，**能拖进度条** |
| 媒体库页 | F5 | **整页不做**，M3 |
| SD 生图页 | F3 | **整页不做**，M4 |

⚠️ **`normalized` 不是装饰，必须显示。** 契约 §2 写清了理由：
用户填 5 秒实际得到 5.17 秒、画布尺寸可能是按首帧图比例推算出来的、
seed 是网关生成的。**不显示的话用户会以为模型不准，或者永远复现不出某个结果。**

⚠️ **`notices` 直接显示，不要按前缀解析。** 它是网关生成的完整中文句子。

## 5. 连不上时怎么区分四种原因

需求 F1 要求分清四种情况，不许统一显示成「网络错误」。

⚠️ **判据分两层，不是一层**：前三种看传输层异常，第四种看**响应体**。
落在 `net/ConnectionOutcome.kt`：

**下表是 2026-09-24 的实测结果，不是推断** —— 四种情况在真机上逐个制造过。

| 判据 | 原因 | 给用户的提示 | 实测 |
|---|---|---|---|
| `UnknownHostException` | MagicDNS 名解析不了 ⇒ Tailscale 隧道没通 | 「手机上的 Tailscale 没连上」 | ✅ 手机上没装 Tailscale 时实测 |
| `SocketTimeoutException` / `NoRouteToHostException` | **没有任何应答** ⇒ 三种可能，见下 | 「服务器没有应答」+ 把三种可能都列出来 | ✅ 杀网关进程、`wsl --shutdown` 各测一次 |
| `ConnectException`（连接被拒绝） | 主机在，但端口没人监听 | 「服务器在线，但网关没启动」 | ❌ **在这台服务器上走不到**，见 §5.0 |
| **HTTP 200 且 `comfy.reachable == false`** | **网关活着，但它报告 ComfyUI 不可达** | 「网关在线，但 ComfyUI 没起来」+ 附 `error` 原文 | ✅ 停掉 ComfyUI 实测 |
| HTTP 200 且 `comfy.reachable == true` | 一切正常 | 在线 + 网关版本 + GPU 名 + 显存 | ✅ 实测 |
| 其他非 2xx | 网关在跑但这个请求出错 | 原样显示状态码与响应体 | ❌ 没构造过 |

⭐ **`comfy.reachable` 那一行是 2026-09-23 补的**（查 `server/app/main.py` 时发现）。
`GET /v1/health` **即使 ComfyUI 挂了也返回 200** —— 网关代码的注释写明这是故意的：
做成 502 会让「网关没起来」和「ComfyUI 没起来」在 App 看来一模一样。

⚠️ **所以「请求成功」不等于「一切正常」。** App 必须再看一眼响应体。

### 5.0 ⚠️ 需求 F1 想分开的两种情况，在这台服务器上分不开

需求 F1 要求把「服务器离线」和「网关进程没起来」分别提示。
**2026-09-24 实测证明在当前环境里做不到**，理由如下。

判别本来靠的是「连接被拒绝」和「连接超时」的区别：
端口关着而主机活着时，正常会收到 RST（`ConnectException`）。

**但这台服务器的 WSL 用的是镜像网络（mirrored networking），
关闭端口上的连接是被丢弃而不是被拒绝。**

实测三种情况，表现完全一样，都是连接超时：

| 制造的情况 | 结果 |
|---|---|
| 杀掉网关进程，WSL 与 Windows 都留着 | 连接超时 |
| `wsl --shutdown` 之后 | 连接超时 |
| （机器关机没测，但没有理由不同）| — |

⇒ **合并成一档「服务器没有应答」，并把三种可能都写进提示里。**
挑其中一种说，等于把用户指向错误的方向 —— 第一版就犯了这个错：
网关进程明明是被杀掉的，App 却说「连不上那台服务器」。

⚠️ **这不是把判据放宽，是把一个被实测推翻的前提改掉**（`Docs/Validation.md` §4.1）。
`ConnectionRefused` 那一档的代码保留着 —— 换个不用镜像网络的环境它就会出现，
而那时它给的信息更精确。**但它至今没有被真实触发过，不算验证过。**

⚠️ **同一个网络行为还引出了一个网关的 bug**，见 §5.3。

**为什么 `UnknownHostException` 能推出「没连 Tailscale」**：
MagicDNS 的域名只有在 Tailscale 隧道建立时才解析得出来（runbook §2）。
所以解析失败 ⇒ 隧道没通。Tailscale 装了但没登录、登录了但断开，都落在这一档 ——
**对用户来说这三种情况的处置动作是同一个**，合成一档是对的。

⚠️ **这张表是一组推断，不是实测结果。** 其中**最可能不准的是第二、三行**：
服务器上 ComfyUI 与网关都跑在 WSL 里，而 tailnet 节点 `icewalnut-1060` 是
Windows 主机（runbook §2）。**WSL 发行版被回收时（ContextPack §4.9 那个坑），
到 7869 的连接到底是被拒绝还是超时，没有测过** ——
Hyper-V 的防火墙曾经把 WSL 的端口从外面全挡住（ContextPack §4.7），
那种情况下表现可能是超时而不是拒绝，于是 App 会把「网关没起来」说成「服务器离线」。

⇒ **这条要在 M2R1 真机实测，编号 VS-31。** 实测结果与这张表不符时，
**改这张表，不要改判据**（`Docs/Validation.md` §4.1）。

⚠️ **不要用「ping 得通吗」来做这个判断。** Tailscale 是用户态网络，
ICMP 的行为与 TCP 不一致；而且真正要回答的问题是「7869 上有没有人应答」，
那只有真发一个 HTTP 请求才知道。

### 5.1 连上之后还有一件事要单独提示：`ffprobe`

`/v1/health` 的 `gateway.ffprobe` 是个布尔值，**为 `false` 时要单独显示一行警告**，
不要混在「在线」里一起显示成绿色。

原因：没有 `ffprobe`，网关**读不出上传图片的尺寸**；而不指定画布尺寸时，
画布就是按图片的宽高比推算的（契约 §2）。读不出来就**静默退回默认尺寸**，
表现为首帧图被拉伸变形 —— **哪里都不报错**。

⚠️ 这是一个**会静默降级**的条件，所以它必须在界面上可见，
而不是等到生成出一个变形的视频才发现。

### 5.2 `comfy` 这个对象的形状是变体的

ComfyUI 可达时有 `gpu` / `vram_total_bytes` / `vram_free_bytes`；
不可达时这三个键**根本不存在**（不是 `null`），取而代之的是 `error`。

⇒ Kotlin 的数据类里这几个字段都要可空并带默认值，
**且必须先判 `reachable` 再取**，不能靠「取出来是不是 null」倒推。

## 6. 任务状态在 App 上怎么呈现

契约的 8 个 `state` 不要原样显示给用户，映射成 4 组：

| 契约的 `state` | App 上显示 | 能做什么 |
|---|---|---|
| `queued` / `preparing` | 排队中 | 可取消 |
| `submitted` / `running` | 生成中（带 `stage`，见下） | 可取消 |
| `postprocessing` | 收尾中 | **不可取消**（契约：返回 409） |
| `done` | 完成 | 播放 |
| `failed` / `cancelled` | 失败 / 已取消 | 看原因 |

**`stage` 的显示是 F2 里点名要求的那一条**：

```text
loading_model   → 「正在加载模型」并说明这一段与生成内容多少无关
sampling        → 「采样中」+ progress 百分比
decoding_video / decoding_audio / encoding → 「解码 / 编码中」
```

⚠️ **`loading_model` 必须单独显示，不能和 `sampling` 合并成「生成中」。**
实测数字：模型已在显存时一次 5 秒视频总耗时约 75 秒，
显存被清空后约 94 秒（M1R7，各 1 次）。
多出来的约 19 秒全部在加载那一段。
⭐ **进程重启后那一次 M2R1 也实测了：92 秒**，和上面两个数差不多 ——
原先担心的「分钟级」并不存在。

⚠️ **但这一条要求不因此取消。** 加载那一段仍然是十几到二十秒，
用户看着一个不动的「生成中」等二十秒，仍然会怀疑是不是卡住了。

⚠️ **M1 阶段 `stage` 与 `progress` 恒为 `null`**（契约 §2 的警告）。
**App 不许把它们为空当成异常** —— 那时显示成不带百分比的「生成中」即可。
它们要等网关连上 ComfyUI 的 ws 之后才有值（§1.1）。

⚠️ **不允许「一定会经过 running 状态」这个假设。**
一个任务完全可能在两次轮询之间跑完，App 会直接从「排队中」跳到「完成」。
对 75 秒的视频任务很少发生，但 M4 接入 SD 之后单张图可能只要几秒。
UI 的状态机要接受任意状态直接跳到终态。

## 7. 轮询策略

**只在「前台 且 有任务未到终态」时轮询。**

| 项 | 取值 | 理由 |
|---|---|---|
| 间隔 | **2 秒** | 采样只有 8 步（约每 9 秒一个进度更新），2 秒已远密于此（§1.2） |
| 什么时候开始 | 进入队列页或详情页，且该任务不在终态 | |
| 什么时候停 | 任务进入 `done`/`failed`/`cancelled`，或页面离开前台 | |
| 后台 | **完全不轮询** | |
| 请求失败 | 连续失败时退避（2s → 4s → 8s，封顶 30s），并在 UI 上显示成「连接中断，重试中」，**不是任务失败** | |

⚠️ **「连不上网关」和「任务失败」是两件事，UI 上不许混。**
需求 §7 写明任务跑在服务器上，App 退后台、切网、重启都不影响任务。
把一次网络抖动显示成任务失败，用户会去重新提交一次 —— 而那要再付一次 GPU。

⚠️ **退到后台就停止轮询，代价是回到前台时状态可能已经变了好几次。**
这没有关系：每次轮询拿回的是完整状态，不是增量（§1.2）。
**「跑完了通知我」是另一个机制**（系统通知 / WorkManager），
**M2 不做**，不要靠提高轮询频率去凑。

## 8. 参考图：M2 只做来源 1（手机上传）

需求 F8 有三个来源，M2 只做第一个：**相册选图 / 拍照 → 上传 → 拿 `asset_id`**。
来源 2（媒体库里挑）是 M3，来源 3（SD 现生成）是 M5。

⭐ **这三个来源在网关那里收敛成同一个 `asset_id` 字符串**（契约 §4 的说明），
所以 M3 / M5 加进来时，**生成页的提交逻辑一个字都不用改** ——
变的只是"那个字符串从哪儿来"。
⇒ **生成页拿到的应当是一个 `assetId: String`，不是一个"上传结果"对象。**

**选图用 Photo Picker**（`ActivityResultContracts.PickVisualMedia`），
**不要申请 `READ_MEDIA_IMAGES` 权限**。Photo Picker 由系统进程提供选择界面，
只把用户选中的那一张的 `content://` URI 交给 App，**不需要任何存储权限**。
申请全相册读权限来做一件"用户自己指一张图"的事，是多要了一个不必要的权限。

**上传用流式**：从 `ContentResolver` 拿 `InputStream` 直接喂给 OkHttp 的
`RequestBody`，**不要先读成 `ByteArray`** —— 手机相册里一张原图几 MB 到几十 MB。

⚠️ **M2 不做裁剪与压缩**（F6 里提到的）。原因：网关**会按首帧图的宽高比推算画布**
（契约 §2 那张表），所以原图直接传上去反而是对的 ——
App 自作主张裁成 16:9 会让网关推出一个用户没要的画布尺寸。
**压缩留到实测上传耗时之后再决定**，现在没有数据支持这个复杂度。

⚠️ **`asset_id` 是一个路径字符串（形如 `grokgen/img_xxx.png`），不是不透明 id。**
App 原样存、原样传回，**不要解析它、不要自己拼**（契约 §3）。

## 9. 播放：M2 的核心，也是 M1 退出标准的最后一块

**用 AndroidX Media3（ExoPlayer）播 `GET /v1/jobs/{job_id}/video`。**

不用系统的 `VideoView`：Media3 的 `DefaultHttpDataSource` 对 HTTP Range
的处理是明确的、可配置的、有日志的，而 `VideoView` 底层的
`MediaPlayer` 在拖动失败时基本不给可用的错误信息。
**而"能不能拖进度条"正是这一轮要验证的东西**，用一个说不清为什么失败的组件去验它没有意义。

⚠️ **拖进度条依赖服务端的 `Accept-Ranges: bytes` 响应头。**
网关已经实现并在 M1R6/R7 实测过（`Range: bytes=0-1023` 返回 206，
`Content-Range: bytes 0-1023/702734`）。
**但那是在开发机上用 curl 验的，不是在手机的播放器里验的** ——
播放器怎么用这个能力（先发一个 range 请求探测、再按需拉取）是另一回事。
⇒ **VS-39 要在真机上验，判据是"拖到中间能从那里开始播"，不是"接口返回了 206"。**

### 9.1 ⚠️ 明文 HTTP 会被 Android 默认拦掉

网关是 **HTTP，不是 HTTPS**（信任边界是整个 tailnet，契约 §1）。
而 Android 从 API 28 起**默认禁止明文 HTTP 流量**。

⇒ 要配 `network_security_config.xml`，
**只对后端那个域名放开明文，不要开全局 `usesCleartextTraffic="true"`**。
全局开等于把 App 发往任何地址的明文请求都放行了，而只有 tailnet 内那一个是可信的。

⚠️ **这一条同时影响接口调用和视频播放** —— Media3 的 HTTP 数据源走的是同一套策略。
**M2R1 第一次发请求时就会撞上**，写在这里是为了不让它变成一次排查。

## 9.5 视觉：主题分层

**上游是需求文档 §7.1**（方向、配色、对比度、排版、间距都在那里，本节不复述值）。
本节只说 **App 内部怎么组织它**。

### 9.5.0 视觉稿在哪

**四张手机画板（生成页 / 队列页 / 任务详情·加载模型 / 任务详情·完成播放）：**

```text
https://claude.ai/artifact/4JzsgFno49g4pzbHbxpkaa
```

2026-09-23 画的，私有，只有仓库主人能打开。
在 Claude Code 里用 `/artifacts` 也能列出来并打开。

⚠️ **它不在这个仓库里，是故意的。** 那个画布是可以在网页上直接编辑的，
往仓库里存一份 HTML 副本，页面上一改副本就过期了 ——
而**没有任何机制会告诉你它过期了**。所以仓库里只留这个链接。

⚠️ **视觉稿是 HTML 画的，不是 Android。** 字体渲染、输入控件行为、
点按反馈、系统栏在真机上都不一样。
**它定的是方向（配色、疏密、层次），定不了像素** —— 真机 Level 4 那一步照做。

⭐ 画布上每张画板都有一个 `accent` 调节项，可以现场换强调色，
**换一下整套界面跟着变** —— 这正是需求 §7.1.2 那句「强调色只是一个 token」的演示。

### 9.5.1 三个文件，一个包

```text
ui/theme/
├── Color.kt      所有颜色 token —— ★ 唯一允许出现颜色字面量的地方
├── Type.kt       字号 / 字重 / 行高的层级
└── Theme.kt      把上面两个装进 MaterialTheme，外加自定义的 status token
```

⭐ **只做深色主题**（需求 §7.1.1），所以**没有 light/dark 两套 token 的分支**。
这省掉的不只是一组值，还有"每个页面要在两套配色下各看一遍"这件事。

### 9.5.2 任务状态的颜色不能放进 `MaterialTheme` 的标准槽位

Material 3 的配色方案里只有 `primary` / `error` / `surface` 这些通用角色，
**没有"排队中"和"已完成"**。硬塞的话会出现
`MaterialTheme.colorScheme.tertiary` 其实是"完成绿"这种只有作者知道的映射。

⇒ 用一个 `CompositionLocal` 挂一组**语义化命名**的 token：

```kotlin
data class StatusColors(
    val queued: Color, val running: Color,
    val done: Color, val failed: Color, val cancelled: Color,
)
```

**名字描述内容不描述出处** —— 是 `done` 不是 `green`。
将来"完成"改成别的颜色时，改的是值，不是所有引用它的地方。

### 9.5.3 状态的呈现不许只靠颜色

需求 §7.1.3 的要求落到代码上：**做一个 `JobStatusChip` 组件，
颜色、文字、图标三者一起给**，各页面只用这个组件，不自己拼。

⚠️ **「排队中」和「已取消」在需求 §7.1.2 里用的是同一个灰** ——
**光看颜色本来就分不开**。这不是无障碍的锦上添花，是功能正确性。

### 9.5.4 可执行的约束：颜色字面量只许出现在 `ui/theme/`

与 §3.1 的分层约束同一个形式，**合并进同一个测试**：

> 扫 `app/src/main/java` 下每个 `.kt`，断言 `Color(0x…)` 与 `#RRGGBB` 形式的
> 颜色字面量**只出现在 `ui/theme/` 下**。

⚠️ **它守的是"设计能不能被一处改掉"。** 颜色一旦散进各个页面，
换配色就变成一次全仓库搜索替换 —— 而那种替换会顺手改到不该改的地方，
**且不报错**。判据是 VS-41。

### 9.5.5 打磨跟着页面走，不集中到最后

需求 §7.1.5 定了：**视觉基础放 M2R1，逐页打磨跟着各自的页面**。
所以本文档 §4 那张页面表里的每一行，**在它自己那一轮里就要做到能看**，
不留"以后统一美化"的尾巴。

⚠️ **这一条对后面的里程碑同样有效**：M3 的媒体库网格、M4 的 SD 生图页，
都在各自那一轮里打磨，**不要攒到最后**。

## 11. 尚未决定的

1. **导航用 Compose Navigation 还是手写一个 sealed class 的状态机。**
   M2 只有四个页面，手写可能更简单；但 M3/M4 会加到七八个。
   倾向先手写，M3 开工时再看。
2. **任务列表的数据来源**：每次进队列页拉一次 `GET /v1/jobs`，
   还是在 App 里存一份本地缓存。M1 的网关**不持久化任务**，重启就丢 ——
   所以本地缓存会出现"App 里有、网关里没有"的条目。**M2 先不缓存**，
   但这意味着网关重启后 App 里的历史任务也跟着消失。
3. **`job_id` 在网关重启后会重复**（TODO 里挡住 M3 的那条）。
   M2 不缓存的话影响为零；将来做本地缓存前必须先解决它。
4. **真机调试用 USB 还是无线 adb。** 手机要连 Tailscale 才能访问网关，
   而 USB 调试不影响这一点，两者应该都可以，没试过。

## 12. 本文档的核对方式

| 结论 | 怎么核对 | 现在的状态 |
|---|---|---|
| `stage`/`progress` 只能从 ComfyUI 的 ws 拿 | 读 ComfyUI 的路由表，确认没有返回"当前执行节点/步数"的 HTTP 接口 | ❌ **未核实**，§1.1 |
| 一次 5 秒视频热启动 75 秒 / 显存清空后 94 秒 | M1R7 冒烟实测，各 1 次 | ✅ 已实测 |
| 采样 8 步 | 网关 turbo profile 的定义 + M1R7 实测配置 | ✅ 已确认 |
| ComfyUI 每步推一个进度事件 | 抓一次 ws 事件流 | ❌ **未核实**，§1.2 |
| 网关的 Range 支持 | M1R6/R7 用 curl 实测 206 + `Content-Range` | ✅ 已实测（**但不是在播放器里**，§9） |
| 四种连接结果的判别 | 真机上分别制造四种情况 | ❌ **未实测**，§5，M2R1 做（VS-31） |
| `/v1/health` 在 ComfyUI 挂掉时仍返回 200 | 读 `server/app/main.py` 的实现与注释 | ✅ **已核实**（2026-09-24），这是故意的设计，§5 |
| `comfy` 不可达时 `gpu`/`vram_*` 三个键不存在而非为 null | 同上 | ✅ **已核实**，§5.2 |
| 明文 HTTP 要配 network security config | Android 官方文档；M2R1 第一次发请求即可证实 | ⚠️ 文档依据，未实跑 |
