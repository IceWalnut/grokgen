# M2 执行文档：Android 原型

**状态**：2026-09-23 初稿，**未开工**
**上游**：`app/Docs/architecture/android_client_architecture_v0.1.md`
**目标**：需求文档 §9 的 M2 —— 连接、上传图片、填 prompt、提交、播放结果。

---

## 1. 退出标准

M2 完成的判据有两条，**都必须在真机上做到**：

> ① **在手机上完整走一遍 I2VA，全程不碰电脑**：
> 填后端地址 → 看到网关在线 → 从相册选一张图上传 → 填 prompt → 提交 →
> 看着状态变化直到完成 → 在 App 里播放结果。
>
> ② **播放时能拖进度条**，且拖动后从拖到的位置开始播。

⚠️ **「接口都调通了」不算完成。** 判据是一次完整的、在手机上做完的生成。

### 1.1 M2 同时要收掉 M1 的最后一条

M1 的退出标准是「下载回一个**能在手机上播放的** H.264 MP4」。
网关侧已经达成（M1R7 冒烟，`scripts/smoke_m1.sh` 退出码 0），
**「手机上能播」这一半至今没验过，因为 App 不存在**。

⇒ **M2R5 的真机播放同时是 M1 的收尾。**
那一步通过之后，回 `Docs/TODO.md` 把 M1 从 🔄 改成 ✅。
⚠️ **在那之前不许把 M1 标成完成。**

### 1.2 M2 不做什么

范围见架构文档 §10。最容易被顺手做进来的三件事，**明确不做**：

| 不做 | 为什么现在不做 |
|---|---|
| 服务端推送进度 | 决定见架构文档 §1：轮询的采样密度已经比进度事件密度高 4 倍以上 |
| 媒体库页、SD 生图页、GPU 状态页 | 对应的契约小节（§4 / §5）**现在还是草案**，照着草案实现等于把未定的形状钉死 |
| 上传前裁剪与压缩 | 网关会按首帧图比例推画布，App 自作主张裁剪反而会让画布变成用户没要的尺寸（架构文档 §8） |

## 2. 前置事实

### 2.1 已经确认的（开工前不用再验）

| 事实 | 在哪确认的 |
|---|---|
| 网关的五个任务接口 + 上传接口已实现并实跑验证 | 契约头部的状态表；M1R1〜R7 |
| `GET /v1/jobs/{id}/video` 支持 Range，返回 206 与正确的 `Content-Range` | M1R6/R7，用 curl 实测 |
| 产物是 H.264 + AAC 的 MP4 | M1R3，服务器上 ffprobe 断言 |
| 一次 5 秒视频约 75 秒（热）/ 94 秒（显存清空后） | M1R7，各 1 次 |
| 开发机有 Android SDK（`android-26`、`android-36`）、JDK 17、adb | `AGENTS.md` §4 |
| 手机装了 Tailscale 并登录同一账号就能访问网关 | runbook §8 |

⚠️ **网关地址、端口、Tailscale 域名看 `Docs/runbooks/home_gpu_server.md` §2，
本文档不复述** —— 那些值有变时只改那一处。

### 2.2 开工前要先确认的两件事

**① 网关是不是活着。** 网关不是开机自启的（用 `setsid nohup` 起的，
TODO 里"升级成 systemd 服务"还没做）。M2 每天开工第一件事是确认它在跑，
方式见 runbook §5.1。

**② 手机能不能访问到网关。** 在写任何 App 代码之前，
**先用手机浏览器打开 `http://<MagicDNS 名>:7869/v1/health`**。
这一步能把「App 写错了」和「网络根本不通」分开 ——
先有 App 再去试，两个原因会缠在一起。

⚠️ **开发机的代理不影响手机。** ContextPack §4.1 那个坑（`http_proxy` 把
Tailscale 请求变成 502，所以 curl 要带 `--noproxy '*'`）**只存在于开发机的 shell 里**。
手机上没有这个代理，**不要在 App 里为它写任何绕过逻辑**。

## 3. Round 划分

命名按项目约定：**M = Milestone，R = Round**，本文档是 M2。

⚠️ **一个 round 不是一个步骤，也不是一条聊天消息**（`AGENTS.md` §1.1）：
它是为解决一个明确问题所做的一次完整努力，内部包含多少次改-构建-测不限。

VS 编号的定义见 `Docs/Validation.md` §3。
**App 侧从 VS-30 起编**（VS-19〜29 预留给网关）。

| Round | 要解决的问题 | 解决的判据 | VS |
|---|---|---|---|
| M2R1 | 手机上的 App 能不能连上网关，连不上时说不说得清为什么（**外加视觉基础**） | 真机上看到网关在线；拔掉 Tailscale / 停掉网关，提示各不相同 | VS-30, VS-31, VS-32, VS-41 |
| M2R2 | 相册里的图能不能变成一个 `asset_id` | 真机选图上传成功，拿到 `asset_id` 与尺寸 | VS-33 |
| M2R3 | 提交的请求体跟契约对不对得上 | 提交成功，`normalized` 与 `notices` 显示在界面上 | VS-34, VS-35 |
| M2R4 | 状态能不能一路看到终态，能不能取消 | 轮询到 `done`；三种取消结果符合契约 | VS-36, VS-37, VS-38 |
| M2R5 | **手机上到底播不播得动** | 真机播放且能拖进度条；一次完整 I2VA 全程不碰电脑 | VS-39, VS-40 |

**验证层级**（`Docs/Validation.md` §2）在 App 这一侧的落法：

| 层级 | App 侧的命令 / 动作 |
|---|---|
| Level 1 构建 | `./gradlew build` |
| Level 2 自动化测试 | `./gradlew test`（JVM 单元测试，不连服务器、不需要设备） |
| Level 2.5 预检 | **App 侧没有对应物** —— 那一层是为了省 GPU，App 不占 GPU |
| Level 3 真实链路 | 真机连网关实跑 |
| Level 4 人眼 | 画面正常、拖进度条顺不顺、起播等多久、**这一页好不好看** |

⚠️ **App 的 Level 2 能覆盖的东西比网关少得多。** 网关那边 workflow 构造、
帧数换算、状态机都是纯逻辑，能在开发机上测；
**App 这边真正的风险（播放、上传、网络分支）全都必须上真机** ——
所以每一轮的判据都落在真机上，`./gradlew test` 只是入场券。

### M2R1 — 工程骨架、连接页，以及连不上时说得清为什么

**问题**：现在 `app/` 是空的。这一轮要回答两件事：
手机上的 App 能不能连上网关；连不上时能不能说清是三种原因里的哪一种。

**要建的东西**：

```text
app/
├── build.gradle.kts / settings.gradle.kts / gradle/libs.versions.toml
├── gradlew（Wrapper）
└── src/
    ├── main/java/com/icewalnut/grokgen/
    │   ├── MainActivity.kt
    │   ├── AppContainer.kt
    │   ├── net/{GatewayApi,GatewayClient,ServerAddress,ConnectionFailure}.kt
    │   ├── data/SettingsStore.kt
    │   ├── ui/theme/{Color,Type,Theme}.kt   ← 视觉基础，见下
    │   └── ui/connect/
    ├── main/res/xml/network_security_config.xml
    └── test/java/.../{LayeringTest,ConnectionFailureTest}.kt
```

这一轮只接一个接口：`GET /v1/health`。

**⭐ 这一轮同时要把视觉基础建起来**（配色、字号层级、间距、圆角、状态色）。
**色值与理由在需求文档 §7.1，组织方式在架构文档 §9.5** —— 两处都不在本文档里重复。

⚠️ **为什么放在这一轮而不是最后**（需求 §7.1.5）：写一次全 App 继承。
不写的话每个页面各自硬编码颜色，到 M4 有七八个页面时再统一，
**要改的是每一个 Composable，而且没有任何机制能帮你找出漏掉的那个**。

⚠️ **但它不许挤占这一轮真正要回答的问题。** 三个文件、不碰业务逻辑；
**这一轮的核心判据仍然是「手机能不能连上网关」**。

**判据**：

| 编号 | 判据 | 层级 |
|---|---|---|
| VS-30 | **分层约束**：扫 `app/src/main/java` 下每个 `.kt`，断言 HTTP 库的 import 只出现在 `net/` 下，且服务器地址/端口的字符串字面量只出现在 `net/ServerAddress.kt` 里 | 1 |
| VS-31 | **四种连接结果被区分开**：手机关掉 Tailscale、服务器关机或 WSL 被回收、网关进程停掉、**网关活着但 ComfyUI 停掉**，四种情况的提示文案各不相同且指向正确的处置动作 | 3 |
| VS-32 | 真机上填入 MagicDNS 地址后，连接页显示网关在线，并显示 `/v1/health` 里的版本信息 | 3 |
| VS-41 | **颜色字面量只出现在 `ui/theme/`**：扫同一批源文件，断言 `Color(0x…)` 与 `#RRGGBB` 形式的颜色字面量不出现在 `ui/theme/` 以外 | 1 |

**VS-41 和 VS-30 写在同一个测试文件里** —— 两者是同一个形式
（扫源码、报具体文件与行号），分两个文件会有两份遍历代码。
⚠️ 同样要**故意植入一次确认它会红**：在 `ui/connect/` 里写一个 `Color(0xFFFF0000)`，
看测试报不报得出那一行，再删掉。
⚠️ 它守的是**「换配色时改一处就够」** —— 颜色散进各页面之后，
换配色就变成一次全仓库搜索替换，而那种替换会顺手改到不该改的地方**且不报错**。

**VS-30 要怎么写**：一个 JVM 单元测试，遍历源码目录读文本、做断言。
**不要写成"不连服务器时测试全通过"** —— 那是个消极判据，
有人在 `ui/` 里直接发请求而测试恰好没走到，它照样是绿的（架构文档 §3.1）。
⚠️ **写完之后故意往 `ui/` 里加一行 `import okhttp3.OkHttpClient` 确认它会红**，
再删掉。一条从未失败过的判据不是判据。

**VS-31 要怎么做**：四种情况要**真的分别制造出来**，不是靠 mock 异常类型。
- 手机上把 Tailscale 关掉 → 期望「没连 Tailscale」
- 网关进程停掉（runbook §5.1），Windows 与 WSL 都还在 → 期望「网关没起来」
- WSL 发行版停掉或服务器关机 → 期望「服务器离线」
- **ComfyUI 进程停掉、网关留着** → 期望「网关在线，但 ComfyUI 没起来」

⭐ **第四种的判据和前三种不一样**：`/v1/health` 即使 ComfyUI 挂了**也返回 200**
（2026-09-24 读 `server/app/main.py` 核实，代码注释写明是故意的）。
所以它要看**响应体**里的 `comfy.reachable`，不是看请求成不成功。

⚠️ **停 ComfyUI 之前先确认它的队列是空的**（ContextPack §4.3），否则会打断正在跑的生成。
⚠️ **重启 ComfyUI 之后的第一次生成很可能很贵** —— 要从磁盘读约 29 GB 模型，
而服务器只有 31 GB 内存装不下。**这个耗时至今没测过**，是 TODO 里挂着的欠账。
⭐ 这一轮本来就要重启 ComfyUI，**正好是测那个数的便宜时机**（不强求，它不是 M2R1 的判据）。

⚠️ **第二、三种很可能和架构文档 §5 那张表对不上。** 网关跑在 WSL 里，
而 tailnet 节点是 Windows 主机 —— WSL 停掉时到 7869 的连接是被拒绝还是超时，
**没有测过**。Hyper-V 的防火墙曾经把 WSL 的端口从外面全挡住（ContextPack §4.7），
那种情况下可能表现为超时，于是 App 会把「网关没起来」说成「服务器离线」。

⇒ **实测结果与那张表不符时，改表，不要改判据**（`Docs/Validation.md` §4.1）。
真分不开时，如实把提示写成「服务器或网关不可达」并**在总结里写清为什么分不开**，
不要假装分开了。

⚠️ **这一轮一定会撞上明文 HTTP 被拦**（架构文档 §9.1）。
网关是 HTTP 不是 HTTPS，Android 从 API 28 起默认禁止明文流量。
配 `network_security_config.xml`，**只对后端域名放开，不要全局 `usesCleartextTraffic="true"`**。

### M2R2 — 上传：相册里的图变成一个 `asset_id`

**问题**：生成任务只带 `asset_id` 不带文件，所以上传是独立的一步。
这一轮要回答：手机相册里那张图能不能完整地传到服务器上。

接 `POST /v1/uploads/image`（`multipart/form-data`，字段名 `file`）。

**要做的**：
- Photo Picker 选图（`ActivityResultContracts.PickVisualMedia`），
  **不申请 `READ_MEDIA_IMAGES` 权限**（架构文档 §8）
- 从 `ContentResolver` 拿 `InputStream` **流式**喂给 OkHttp，不要先读成 `ByteArray`
- 显示上传进度与结果（`asset_id`、`width`、`height`、`size_bytes`）

**判据**：

| 编号 | 判据 | 层级 |
|---|---|---|
| VS-33 | 真机从相册选一张图上传成功，返回的 `width`/`height` 与那张图的实际尺寸一致，且 `asset_id` 带 `grokgen/` 前缀 | 3 |

⚠️ **判据里的"尺寸一致"不是多余的。** 网关的 `width`/`height` 是从落盘文件读的，
而**不给生成任务指定尺寸时，画布就是按这两个数推出来的**（契约 §2）。
这两个数错了，画布会跟着错，而**那不会报错**，只会让首帧被拉伸变形。

⚠️ **`asset_id` 原样存、原样传回，不要解析。** 它是一个相对 ComfyUI `input/` 的路径。
⚠️ **重名的图 ComfyUI 会自己改名**，所以要用返回值里的 `asset_id`，
**不能拿本地文件名去拼** —— 网关侧 VS-15 专门测过这条，
用错名字会引用到另一张图**且不报错**。

### M2R3 — 生成页：提交一个 I2VA，并把网关改了什么显示出来

**问题**：请求体的形状对不对，以及**用户要的和他会得到的差别有没有告诉他**。

接 `POST /v1/jobs`。M2 只做 T2VA 与 I2VA（**FL2VA 不做**）。

**要做的**：
- 模式选择、三段 prompt（画面描述 / 环境声 / 背景音乐，
  **UI 上用带说明的输入框，不要把英文键名甩给用户**）
- 首帧图槽（接 M2R2 的结果）
- 时长、turbo 开关、seed（可留空）
- **`width`/`height` 默认不填**（契约 §2：默认应当是"不给"，让画布去适配图片）
- 提交后显示 `normalized` 九个字段与 `notices`

**判据**：

| 编号 | 判据 | 层级 |
|---|---|---|
| VS-34 | 提交请求体与契约逐字段一致：对一个固定的表单输入，序列化出的 JSON 与一份 golden 文件相同 | 2 |
| VS-35 | 真机提交后，界面上能看到 `actual_duration_seconds`、`width`/`height`、`seed`，以及 `notices` 的中文句子 | 3/4 |

**VS-34 为什么要 golden 文件**：请求体有十几个字段，
其中 `width`/`height`/`steps`/`seed` **留空时必须是 `null` 而不是被省略或写成 0**。
⚠️ 网关那边 pydantic **会把没声明的字段直接丢掉，不报错**
（ContextPack §4.005 实测过一次）—— 所以 App 多传一个字段、
或者把 `null` 写成了别的东西，**请求照样 200、任务照样成功**，只是行为不对。
逐字段比对 golden 是唯一能挡住这类错的办法。

⚠️ **golden 文件不提供自动覆盖开关**（`Docs/Validation.md` §2 Level 2）。
有了它，"改坏了"和"改好了"就是同一个动作。

**VS-35 为什么重要**：契约 §2 明确写了 `normalized` 不是装饰。
用户填 5 秒实际得到 124 帧 = 5.17 秒；不填尺寸时画布是按首帧图比例推算的；
seed 是网关生成的。**这三个不显示，用户会以为模型不准，或永远复现不出某个结果。**

⚠️ `notices` 是网关生成的完整中文句子，**直接显示，不要按前缀解析**。

### M2R4 — 队列页：看着它跑完，以及取消

**问题**：状态能不能一路看到终态；取消的三种结果 App 认不认得。

接 `GET /v1/jobs`、`GET /v1/jobs/{id}`、`POST /v1/jobs/{id}/cancel`。

**轮询策略见架构文档 §7**：2 秒一次，只在前台且任务未到终态时轮询，
连续失败时退避到封顶 30 秒。

**判据**：

| 编号 | 判据 | 层级 |
|---|---|---|
| VS-36 | 轮询在任务进终态后停止，App 退到后台时停止；**判据是数请求次数**，不是"看起来停了" | 2/3 |
| VS-37 | 取消的三种情形 App 都处理正确：排队中取消 → 变 `cancelled`；运行中取消 → 变 `cancelled`；**对终态任务取消返回 409 → 显示"已经结束了"，不是崩溃也不是"失败"** | 2/3 |
| VS-38 | **网络中断后任务仍在跑**：轮询途中把手机 Tailscale 关掉几十秒再打开，任务最终仍能走到 `done`，App 显示的是"连接中断，重试中"而不是"任务失败" | 3 |

**VS-36 怎么数请求次数**：在 `GatewayApi` 外面套一层计数的装饰器，
单元测试里驱动生命周期事件并断言计数。
⚠️ **不要用"跑一会儿看日志"来判**，那判不出"多轮询了几次"这种问题。

**VS-37 那条 409 是重点**：契约里 409 和 404 是完全不同的意思 ——
404 是"这东西不存在，别再问了"，409 是"状态不对/再等等"。
⚠️ **混成一个，App 就不知道要不要继续轮询**（契约 §2 的警告）。
`GET /v1/jobs/{id}/video` 在任务没到 `done` 时也返回 409，同一个道理。

**VS-38 对应需求 §7 的"任务持久性"**：任务跑在服务器上，
App 退后台、切网、重启都不影响它。
⚠️ **把一次网络抖动显示成任务失败，用户会重新提交一次 —— 那要再付一次 GPU。**

### M2R5 — 播放：M2 与 M1 的共同退出标准

**问题**：**手机上到底播不播得动。**
这是 M1 退出标准里唯一没达成的那条，也是整个 M2 的核心。

接 `GET /v1/jobs/{id}/video`，用 Media3（ExoPlayer）播。

**判据**：

| 编号 | 判据 | 层级 |
|---|---|---|
| VS-39 | **真机上能拖进度条**：拖到视频中段，**从拖到的位置开始播**，画面与音频都正确 | 3/4 |
| VS-40 | **一次完整的 I2VA 全程不碰电脑**：填地址 → 选图上传 → 填 prompt → 提交 → 看状态 → 播放，全部在手机上做完 | 3/4 |

**VS-39 的判据为什么是"从拖到的位置开始播"，不是"返回了 206"**：
网关的 Range 支持在 M1R6/R7 用 curl 验过（`bytes 0-1023/702734`），
**而且逐字节比对过返回内容** —— 那一层已经有证据了。
这一轮要验的是**播放器怎么用这个能力**，那是另一回事：
响应头正确但播放器拿到错误的字节，表现就是拖动后画面错位，
**而这只有真的拖一次才看得出来**。

**VS-39 还要记下的两个观察**（Level 4，没有自动判据，但必须写进总结）：
- **起播要等多久**（从点播放到出画面）
- 拖动之后**要缓冲多久**才恢复播放

⚠️ 这两个数没有"多少算合格"的标准，**但要有数**。
将来网络或文件大小变了，只有先记下一个数才比较得出来。

**VS-40 通过之后**：
1. 回 `Docs/TODO.md` 把 **M1 从 🔄 改成 ✅**，并注明是被 M2R5 收掉的
2. 更新 `server/Docs/implementation/M1_gateway_mainline.md` §1.1 那张表的最后一行

⚠️ **这两件事要在同一次改动里做完。** M1 的完成状态记在两个文件里，
漏掉一个就会出现"一份说完成一份说没完成"。

## 4. 会咬人的，按会不会撞上排

### 4.1 明文 HTTP 被 Android 默认拦掉（**M2R1 必定撞上**）

见架构文档 §9.1。配 `network_security_config.xml`，只放开后端域名。
⚠️ **这一条同时影响接口调用和视频播放**，Media3 走的是同一套策略。

### 4.2 开发机的代理不影响手机（**别顺手写绕过逻辑**）

ContextPack §4.1 那个坑（curl 要带 `--noproxy '*'`）**只存在于开发机的 shell 里**。
手机上没有这个代理。**在 App 里为它写任何东西都是错的。**

### 4.3 `adb` 不在 PATH 里

全路径是 `~/Android/Sdk/platform-tools/adb`（`AGENTS.md` §4）。

### 4.4 系统默认 `java` 是 11，不要动它

项目通过 Gradle toolchain 声明 JDK 17。
⚠️ **不要 `update-alternatives` 切换全局 java**（`AGENTS.md` §4）。

### 4.5 `stage` 与 `progress` 现在恒为空，不是 bug

契约 §2 写明了。**App 不许把它们为空当成异常。**
它们要等网关连上 ComfyUI 的 ws 才有值（架构文档 §1.1）。

### 4.6 不许假设任务一定会经过 `running`

一个任务可能在两次轮询之间跑完，直接从"排队中"跳到"完成"。
UI 的状态机要接受任意状态直接跳到终态（架构文档 §6）。

### 4.7 网关重启后任务列表会空

M1 的网关不持久化任务。M2 不做本地缓存，所以网关一重启，
App 里的历史任务跟着消失 —— **这是当前的真实行为，不是 App 的 bug**。

### 4.8 跑 GPU 验证前先看 ComfyUI 忙不忙

每一轮里凡是真提交生成的，都要先确认队列是空的（ContextPack §4.3）。
一次 5 秒视频约 75 秒（热）。**M2 有五轮，别在一轮里反复提交烧 GPU** ——
调 UI 时用一个已经跑完的任务的 `job_id` 就够了。
